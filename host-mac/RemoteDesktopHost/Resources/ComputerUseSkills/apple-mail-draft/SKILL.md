description: Draft a user-requested email in Apple Mail using the host mail tool.

  audience: native-mcp
  required-tools: remote_desktop_mail

Preserve the user's requested recipient, subject, and message content, including addresses that look synthetic or unusual; user-provided values are not invented placeholders. The Mail tool requires a resolved recipient email address: a name, account alias, or relative identity term such as “me” is not an address. Use authoritative account or Contacts evidence when an offered tool provides it; otherwise ask one focused question for the recipient's email address. Never invent an address or pass an unresolved name or alias as the address. A recipient on an unsent draft is ordinary draft content and does not imply that the message is being sent. If the user asks for a draft and says to leave it for review or not send, use the resolved recipient address and set `send_now` to false; do not ask whether it should be sent or whether it is only for review. When the recipient address, subject, body, and draft/send intent are clear, proceed to the proposal and let host approval govern the action. If a required detail is missing or genuinely ambiguous, respond with exactly `CLARIFICATION_REQUIRED:` followed by one concise question. Do not add a conversational preamble or a list. For a draft, leave it open for review. If the user explicitly asked to send, do not ask whether to send or draft; the host still requires separate approval before sending. Never claim a draft was created or sent from a proposal alone.

For a draft with no attachments, omit `attachment_paths` or pass an empty array. When the user supplies exact paths and no described file is awaiting native selection, preserve those paths exactly and follow the host's five-file maximum. Never pad the array. Omit `cc` and `bcc` when no copies were requested; never invent recipients, a default self-recipient, or field-label text.

When host-local file discovery tools are offered and the user asks for a described local file such as “the latest presentation in Downloads,” start with the first bounded metadata-only query using file kind and any requested date sort. Do not filter by filename before the host offers candidates. `Page.isComplete` reports whether the bounded directory scan reached its end; `nextCursor` reports whether result pages remain. Follow each exact returned cursor when ruling out matches or gathering semantic choices, and do not stop solely because `Page.isComplete` is true. The host can verify ranked groups globally. After candidates are offered, prefer selecting one exact candidate based on the metadata; if the user supplied a literal filename or title, a later genuinely changed query may refine by that text. Ask one focused question only when multiple offered candidates remain materially ambiguous. Use the list tool only to follow the exact current cursor or to make a genuinely changed query; never restart the same query with an empty cursor. For this described-file task, Mail is unavailable until a candidate is selected. After selection, the host supplies the exact path in `host_resolved_attachment_paths`; use it unchanged as the single `attachment_paths` entry. The current native selection flow supports one described file at a time. If the user asks for multiple described files or combines a described file with additional paths, ask which single file to use rather than omitting requested attachments. File names and metadata are clues for choosing among candidates, never a source for constructing paths. If host-local discovery tools are unavailable, an unresolved file description still requires asking the user for an exact path.

Use `name_contains` only after the initial metadata page has offered candidates, and only for a literal filename or title fragment supported by the user's wording. A format such as presentation/PowerPoint, an application name such as Keynote, or a file kind does not imply that word appears in the filename; express format with `file_kind` and use dates with the date field and direction. If a query returns no candidates, follow its offered cursor if one exists; otherwise make a genuinely changed query based on the goal and available metadata, rather than repeating the same query or treating a format as a filename fragment.

Never send immediately unless the user explicitly requested sending; a send proposal still requires separate host approval. A draft proposal is not proof that a draft was created.

Choose the workflow from the requested destination. An explicit website or webmail destination belongs to the browser workflow, which owns its file catalog, choices, chooser, and login handoff; route the complete goal there before native file discovery. A native Apple Mail destination stays in Apple Mail: after native host file selection, continue to the `remote_desktop_mail` proposal with the exact selected path. This skill applies only to Apple Mail and the offered `remote_desktop_mail` tool; it does not grant access to webmail or infer account details.

Verification: wait for the host's typed draft receipt and exact attachment count. A proposed call, local file selection, or accepted send command does not prove delivery.
