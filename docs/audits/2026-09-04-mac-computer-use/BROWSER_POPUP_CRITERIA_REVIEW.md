# Preserving observed criteria through dropdown opening

Source checkpoint following `41e7cbf`. [Option selection is connected to research](BROWSER_OPTION_SELECTION_DRIVER_REVIEW.md), but opening the dropdown previously required only metadata and could change another criterion before selection captured its baseline. This checkpoint requires scoped inspection before opening, binds observed criteria to the opening operation, and retains those original values into subsequent choice/read preparation. The source remains uncompiled and unexecuted.

## First-principles failures and repair

The baseline must precede the effect it constrains. Reading a date after a dropdown handler has reset it cannot establish that the user's original date was preserved. A receipt that proves only that the list became visible also cannot establish that opening left selection or other settings intact.

There are two separate obligations: determine which criteria the complete request requires, then preserve the criteria actually observed. This checkpoint implements stronger capture, identity, comparison and recovery for the latter. It does **not** prove that the model selected every semantically required control. A model that omits the date from the first scope can still omit its preservation obligation. Complete scope review remains the first follow-up below; prompt instructions alone do not close it.

An explicit failed reading also must not disappear from the contract. Previously an unavailable scoped control could be skipped when collecting preserved values. Both popup and selection preparation now reject unavailable or stateless additional controls in their explicit scope. Unscoped values remain unread; the change does not authorize reading all fields.

## Prepared verification and evidence limits

Ten new methods in [popup criterion coverage](../../../host-mac/RemoteDesktopHostTests/ComputerUseBrowserPopupCriteriaTests.swift) specify:

1. Metadata alone cannot construct an opening intent, decode an opening proposal or allocate a native opening binding.
2. A changed date under the same snapshot changes the popup baseline/contract; receipts require the preserved IDs and journals omit raw task, criterion, choice and binding values.
3. A handler that resets, replaces, reinserts or changes the disabled status of an observed date cannot confirm; acknowledgement cannot dispatch twice or falsely retire the attempt.
4. Opening cannot change the owner's existing selection or native combobox input value.
5. An explicitly scoped unavailable criterion cannot be dropped by native or host opening/selection eligibility and intent validation.
6. An observed date reset or owner-label change remains uncertain after restoration and exact stage reopening.
7. The driver inspects the date before opening, carries it through one selection and reads fresh evidence under the full original task, producing only a partial report.
8. A date changed after a confirmed opening blocks both the next choice and result reading; historical and current values remain distinct in action context.
9. A confirmed ticket selection does not release the original date before result reading.
10. An unsent popup retirement after manual handback retains its original date and journal statuses, blocking a replacement opening against the changed baseline.

Existing native and research popup fixtures now inspect before opening. The unsupported-submit fixture uses its own referenced list ID so it does not create a second ambiguous owner for the valid control. Existing failed-write, cancellation, no-replay and login-handback cases remain selected. Model responses in these fixtures are authored decisions, not evidence that a lightweight model chooses the right scope.

All fourteen changed/new Swift files pass syntax-only parsing; subsequently edited files were parsed again. The assembled production DOM with four fixed fragments and thirteen fixture JavaScript variants pass `node --check`. The [default inventory](../../../host-mac/AcceptanceFixtures/osatlas-deterministic-tests.json) matches **1,273 source methods**, and the [focused inventory](browser-control-state-inventory.json) matches **590**, with ten additions and no removals. The two new Swift files each have four Xcode registration entries, and project syntax is checked. Local documentation links and whitespace are checked before commit. No build, typecheck, test assertion, JavaScript execution, app/browser/computer-use launch, model run or held-out inspection/run occurs.

These checks prove source syntax and reviewed registration, not runtime behavior or race coverage. A cached native receipt is historical evidence at its observation time. Property changes restored between observations, arbitrary handler requests and provider state are not continuously monitored or fenced. The new checks cannot establish that every instant of an interaction preserved a value or that no other side effect occurred.

## Remaining repair order

1. Establish complete preservation scope under the whole request before an effect. Reuse the existing distinction between complete metadata, relevant/unrelated controls and unresolved omissions; require explicit source-backed decisions for criteria rather than accepting an owner-only read as sufficient. Carry actual original requirement references for each obligation. Cover omitted dates, compound requirements, unrelated private fields, missing/oversized metadata and ambiguous controls. Do not solve semantic omissions by automatically reading every field.
2. Replace the conservative retained-observation rule with explicit task criterion lifetimes and permitted changes. Carry unchanged obligations across successful selection, form editing/query, scrolling, history/navigation, new pages and login returns. An intentional change needs a goal-backed replacement; an accidental reset must retain the old obligation. Distinguish “preserve during this effect,” “keep for the task” and “change as requested.” The current same-document checks can conservatively stop legitimate workflows until this reconciliation exists.
3. Connect criteria to accepted application values and causally fresh result predicates. A visible list or selected flag cannot prove correct travel dates, class, fees, stock or availability. Reconcile already-retained form receipts and query criteria instead of admitting a fresh baseline from post-effect page state.
4. Extend explicit support for lazy, rebuilt and virtualized widgets and account/provider transitions. Review handler/network/navigation semantics and transient state changes separately from DOM receipt identity. Do not describe synthetic clicks as proving absence of arbitrary website side effects.
5. Complete durable parent task/criterion history across process and browser-session loss. The native ledgers and owner histories remain session-local; child journals alone do not reconstruct them. Qualify callback and store-recovery behavior through the actual host/control lifecycle.
6. Keep execution deferred until the user authorizes it after development readiness. Then qualify real model scope/action decisions, visible account handoff, travel/concert/movie website tasks and whole-app resource use. The authorized RTX 3080 desktop, alternate models and possible adaptation remain options after measured failures; SSH/hardware access, 8 GB operation and thermal behavior are still unqualified.
