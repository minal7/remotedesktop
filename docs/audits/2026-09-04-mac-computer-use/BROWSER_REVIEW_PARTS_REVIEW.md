# Completing bounded review output without dropping task requirements

Source checkpoint, 2026-09-08. Previous checkpoint: `0ae88dd`. Runtime and model execution remain deferred.

## First-principles problem

The requirement review can describe up to eight candidates, sixteen fields per candidate and thirty-two original requirements. Asking for all those judgments in one 1,024-token response creates an output-capacity failure even when the input fits. Removing requirements would change the task; removing surrounding page context could hide competing offers and qualifications. Giving each smaller request a new full timeout would instead turn one review into potentially prolonged, unbounded work.

The repair divides requested **output** while retaining one immutable full input. Only a complete, consistently bound review may reach the research owner. This is a correctness/capacity repair, not performance or 8 GB qualification.

## Source implementation

- [Output planning](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserReviewParts.swift) estimates conservative canonical JSON size using the longest enum spellings and up to eight longest observed reference IDs. A complete response whose estimate is at most 896 bytes keeps the existing single-call path. Otherwise the host plans ordered parts, each for one candidate and at most four field/four requirement rows, reducing the requested rows until the same size estimate fits. Every original field and requirement appears exactly once. Planning rejects work exceeding 32 parts before inference, with the full task unchanged.
- Every part carries the original [review input](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultReview.swift): complete goal, accepted answers, original clock, requirement ledger, page projection and all candidate context. `requested_output` specifies only which indices to return. The model does not choose, reorder or omit parts, and another candidate's page text remains visible as context without becoming that candidate's citation authority.
- Part decoding requires a closed object, exact candidate and ordered field/requirement indices, known enums and distinct observed references. Requirement references cannot borrow another candidate's text. Duplicate JSON keys, missing rows, unknown references and malformed responses fail before another part is requested.
- The assembler accepts only its next exact part, bound to the original native input. It rejects duplicate, missing, foreign or inconsistent parts. All parts **for the same candidate** must agree on association; separate candidates may have different associations. The assembler exposes no partial review to planning, reporting or completion.
- Once all parts arrive, the normal full-review checks run again: field kinds/scopes, price qualification, complete requirement coverage, whole relevant fields, source references, incomplete-page restrictions and candidate ownership. Combining syntactically valid parts cannot bypass these checks. The internal assembled representation has a 32 KiB ceiling and reference ceilings derived from the original field/requirement dimensions; individual untrusted response decoding retains its existing 16 KiB ceiling. This larger internal representation does not raise model response or context budgets.
- The [local planner](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultReviewPlanner.swift) runs parts sequentially on the existing transport and worker. Every request is token-counted against the unchanged 4,096 context / 1,024 output / 64 framing budgets. All count, completion, decode and assembly work shares a single monotonic deadline capped at 30 seconds. Completion requests receive the remaining timeout, and cancellation/deadline checks occur before later requests and before publication. A structured task group races the entire review against that deadline, cancels in-flight work on expiry and joins its cleanup. This is necessary because token counting internally makes two HTTP requests with independent timeouts; passing a timeout alone is insufficient. The current transport cancels its actual URLSession request on cancellation. Returning still depends on cooperative transport cleanup; the owner is not released early if cleanup stalls. A failed, late or cancelled part discards the speculative prefix; there is no automatic retry or partial-success promotion.
- The [research driver](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResearchDriver.swift) reports a review deadline as a resumable intervention on the original task. Native current-page/goal validation still follows the complete model review. No part can navigate, submit a form, finish login or complete the original research request.

The 896-byte estimate is a conservative canonical-output sizing rule, **not an exact tokenizer bound, latency measurement or a guarantee of model compliance**. Extra whitespace, refusal, truncation, conflicting judgments and context overflow remain failures. Full input context is never silently trimmed to make a part fit. Calls are bounded per review; whole-task resource/thermal behavior still needs qualification.
