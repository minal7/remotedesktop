# Fresh capture needs one display identity, a bounded request and real media evidence

Evidence and implementation design; **no runtime repair is claimed in this review**. This follows [bounded initial startup](CAPTURE_STARTUP_REVIEW.md). Source and SDK review found a display-identity defect that must be repaired before adding a screenshot recovery path. No build, typecheck, test/assertion execution, native capture, app/device/browser operation, model run or SSH retry was performed. Public Apple documentation was retrieved read-only.

## Confirmed display-identity defect

[ScreenCapture.makeStream](../../../host-mac/RemoteDesktopHost/ScreenCapture.swift) selects the display matching `CGMainDisplayID()`, falling back to the first discovered display. It constructs the content filter and output configuration locally, then returns only the SCStream. The peer does not retain that selected display's identity, bounds or filter as part of its input scope.

[HostPeerSession.sendHelloAckAndDisplay](../../../host-mac/RemoteDesktopHost/HostPeerSession.swift) independently reads `NSScreen.main.frame` and `backingScaleFactor` each time it sends the layout. The installed [AppKit header](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/AppKit.framework/Headers/NSScreen.h:31>) identifies this as the screen with the key window. It is not a binding to the display selected by ScreenCaptureKit. The [CoreGraphics header](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/CoreGraphics.framework/Headers/CGDirectDisplay.h:113>) defines display bounds in the global display coordinate system, including their origin.

The [phone geometry](../../../ios/RemoteDesktop/Session/RemoteScreenView.swift) derives both its interactive rectangle and screen-local coordinates from the advertised width/height. [InputInjector](../../../host-mac/RemoteDesktopHost/InputInjector.swift) passes those coordinates directly to CGEvent without a captured-display origin or transform.

Consequences inferred from these source paths:

- Focusing a window on a differently sized monitor can change the advertised layout while capture still shows the original display. A new/duplicate hello can then publish the wrong dimensions under the same input scope.
- The fallback capture display need not have global origin zero. Its screen-local phone coordinates can target another part of the desktop.
- Display rearrangement, main-display changes, rotation and resolution/scale changes are not bound to the input session. Correct geometry at startup does not establish correct geometry later.
- The video surface can have encoder-scaled dimensions or letterboxing. Treating logical display dimensions as a complete description of actual content placement is not sufficient for all layouts.

These are validated source mismatches and conditional failure paths, not reproduced native misclicks. No multi-monitor/device run was performed.

## Native screenshot evidence and its limits

The installed [SCScreenshotManager header](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ScreenCaptureKit.framework/Headers/SCScreenshotManager.h>) exposes `captureSampleBuffer(contentFilter:configuration:completionHandler:)` from macOS 14, matching the host deployment target. It accepts an explicit content filter and stream configuration. Apple's [WWDC23 introduction](https://developer.apple.com/videos/play/wwdc2023/10136/) describes asynchronous still capture without creating an SCStream. The [class reference](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager) offers both sample-buffer and image output.

The reviewed material does not specify that screenshot output always has complete-status/display-time attachments, that its WindowServer display time exceeds the request's host-clock lower bound on an unchanged desktop, or that it is drawn from the exact active SCStream object. Those remain unanswered requirements, not guarantees to invent. Reusing a filter/configuration establishes intended content selection; it does not alone establish frame freshness or stream continuity.

The [SCStream SDK header](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ScreenCaptureKit.framework/Headers/SCStream.h:418>) gives display time the meaning of the WindowServer display event. Callback arrival time has a different meaning. A screenshot callback must not overwrite missing/older native capture evidence with `mach_absolute_time()` and label that replacement as capture time.

A successful still-image request also does not prove that the continuing stream has resumed after blank/suspended output. This is an architectural inference: the request does not name that stream object and its success does not assert that stream's future update behavior. Otherwise one fresh still could reopen input while later actions are shown against a frozen screen.

Apple's [capture pipeline discussion](https://developer.apple.com/videos/play/wwdc2022/10155/) explains that held surfaces reduce the server's available surface pool and can cause stalls. A screenshot repair must therefore have bounded native request and buffer ownership. Cancellation of a waiting task must not be treated as proof that the underlying capture operation released its resources.

## Implementation order and acceptance requirements

1. **Bind the actual capture target.** Retain an immutable descriptor with the capture owner and native attempt: selected display ID, global logical bounds, backing scale, capture filter/configuration and output geometry. Use one descriptor for video interpretation, layout publication and direct-input mapping. Do not sample a focus-dependent screen in the hello encoder. Do not rediscover a different display merely because a fresh-image request is starting.
2. **Retire input when that descriptor changes.** Geometry changes must invalidate the old input/presentation scope, release held controls and require a new scoped layout/frame. Retain the descriptor with the injector's exact local session; a packet admitted before the change cannot be mapped using replacement geometry. Recheck native target validity at posting without taking the capture gate while holding the injector lock. Keep the existing capture → authorization → injector lock order intact.
3. **Define one coordinate transform.** Convert the phone's coordinates from the captured content rectangle into the selected display's global logical coordinate system. Account for encoder scaling, content padding, origin and rotation. Validate finite/ranged dimensions and coordinates before integer conversion. Preserve the mapping for releases belonging to an old held gesture; never use that cleanup to release a successor's controls. Keep AI/global-desktop injection distinct from the screen-local phone protocol.
4. **Create an exact fresh-image request lease.** Bind each request to owner, native attempt, input/recovery generation, descriptor revision, request ID and a host-clock lower bound. Admit it under the existing capture gate, then release that gate before invoking the asynchronous screenshot API. Revalidate the exact lease and deadline when its callback returns. A newer loss, display change, close or replacement permanently retires that result.
5. **Bound the real operation.** Allow one outstanding native still-capture operation for the shared capturer, including across owner replacement. Keep its capacity occupied until the actual callback completes even if the consumer times out or cancels. Bound retries within the original availability episode. Release discarded buffers promptly; do not retain an archive or create an unbounded series of abandoned requests. Preserve the real teardown barrier separately from the caller's timeout result.
6. **Prove what the returned image means.** Start with the actual sample-buffer attachments and format. Require valid, ready pixels and supported native timing/geometry evidence. If metadata cannot prove freshness on static content, choose and qualify a native witness that can; do not relabel callback time or relax the rule silently. Record still-request success separately from continuing-stream availability until the continuity requirement is satisfied.
7. **Carry that evidence through the actual video.** Bind the challenge and exact source frame through encoding, transport, decode and the owning renderer. An unrelated data-channel receipt or independent decoder probe is insufficient. Preserve the [existing media-proof work](CAPTURE_FRAME_EVIDENCE_REVIEW.md#detailed-sequence-to-close-the-actual-recovery-gap), including pinned binary provenance, timestamp transformation and render ordering. Rearm this evidence on foreground return and relevant display/track changes.
8. **Qualify native and task behavior later.** After explicit permission, cover unchanged desktops, blank/suspended/resumed streams, late screenshots, missing attachments, native hangs, multi-monitor focus/rearrangement/rotation, encoder padding, old queued input, held gestures, foreground return and actual presentation. Then verify preservation of the exact paused login task and deliberate Resume before the deferred travel/concert/movie scenarios. Model and 8 GB resource qualification remain later work.
