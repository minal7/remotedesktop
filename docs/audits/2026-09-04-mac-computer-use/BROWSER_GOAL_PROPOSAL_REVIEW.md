# Retain research requirements before compiling browser actions

Date: 2026-09-07. Parent source: `5432f91`. New no-effect planner component and runtime entry point. **Not connected to browser task routing; no autonomous research capability is claimed.**

## First-principles finding

The explicit browser driver can execute a complete sequence of supported commands. The semantic GUI route can propose the next action. Neither currently supplies the retained interpretation and result requirements needed for an ordinary request such as finding three flights on a particular date under a total-price limit. More target checks alone do not fill that architectural gap.

The prior form proposal code contains a useful coverage check, but coverage is not meaning. A model can copy every word while assigning an origin to the destination field, reversing a comparator, or treating a prohibition as an action. A source fragment and a valid JSON schema cannot certify that interpretation. This component deliberately returns a **proposal**; it does not construct a `ComputerUseTaskContract`, dispatch a browser action, present a question or report completion.

## Implemented boundary

1. `ComputerUseBrowserGoalInput` retains exact original request bytes, root task ID, fixed reference time in milliseconds and an explicit time-zone identifier. Its digest binds all four. It rejects empty/oversized requests, invalid task IDs, invalid clock values and unknown time zones. Relative dates remain anchored to the same input instead of changing meaning each time Resume runs.
2. The proposal retains an ordered requirement for every source fragment. Roles distinguish outcomes, conditions, prohibitions, order, clarification and unsupported work. Fields include categories, routes, locations, dates/times, quantities, price, fees, availability, sorting and sources; `other` retains requirements outside that vocabulary. Comparators and verbatim value hints are model interpretations, not executable arguments.
3. Source fragments must concatenate to the exact original UTF-8 sequence, including whitespace, punctuation, repeated text and Unicode normalization form. The host assigns offsets and stable requirement IDs from the input, occurrence, source and proposed interpretation. Hints must occur byte-for-byte within their own fragment. Missing tails, duplicated/added work, reordered fragments and hints borrowed from other requirements are rejected.
4. Strict decoding rejects duplicate/unknown keys, invalid enums, bounds violations and contradictory dispositions. A `research` proposal must contain an outcome and cannot also claim unresolved/unsupported requirements. Clarification and unsupported dispositions still retain the complete original source. A question is merely proposed and is permitted only with a clarification disposition.
5. The local model receives only the original request and its fixed time context. This component supplies no page/account observation, performs no credential reads, and has no browser executor or input injector. The response schema is closed and bounded; context is JSON encoded. The original request is never reduced to fit the model. Existing request identifiers and proposal digests stay host-side.
6. The same complete request is token-counted and then submitted once, with a 4,096-token context, 1,024-token output allowance, 64-token framing reserve, deterministic sampling and prompt caching disabled. Nonpositive or excessive counts stop before completion. There is no correction/retry loop or fallback that could discard requirements after a malformed answer.
7. Response admission requires the expected served-model alias, one stopped assistant choice and textual JSON, without active tool calls or refusal content. Invalid UTF-8, oversized responses, duplicate envelope keys, incomplete generations, another model or a different request's source are rejected. Cancellation is checked before counting, before inference and before returning a proposal.
8. `ComputerUseRuntimeBrowserGoalPlanner` and `OSAtlasLlamaRuntime.proposeBrowserGoal` share the existing verified native text installation and model owner. The runtime holds its model-access lease through resource admission, counting, inference and decoding; endpoint generation and cancellation are checked. This adds no independent server or new process lifecycle policy. It is a callable component for the forthcoming driver, not a new route enabled in the host.
9. Default descriptions contain only counts/dispositions and role/field names. They do not expand task text, value hints or proposed questions into logs. Raw input and proposal data remain in memory; this change does not add a durable transcript or claim recovery after a host restart.

The planner and prepared test file are registered in the Xcode targets. SwiftPM and `project.yml` already include their directories.

## Prepared verification and limits

Seven methods cover complete ticket-request retention, repeated identical fragments, exact offsets, negation/comparison retention, omitted/reordered/added work, Unicode byte fidelity, scoped hints, task/clock/time-zone identity, malformed schemas, unresolved dispositions, closed model input, exact token admission, response integrity and cancellation. One case deliberately retains a model's wrong field interpretation as a proposal: this documents that the decoder cannot establish semantic correctness and must not be used as an action/completion gate.

The [focused source inventory](browser-goal-proposal-inventory.json) selects **223** methods; the default selects **745**. Three changed/new Swift files pass syntax-only parsing; project-file syntax, source inventories and whitespace checks pass. **No typechecking, assertions, models, builds, app launches or computer-use activity ran.** No actual-model evaluation, prompt qualification, tool-schema runtime compatibility, 8 GB measurement or thermal evidence exists for this new contract. The existing installed app is unchanged.

## Required integration work

1. Retain one goal input and interpretation in the actual browser task driver. Create its clock once; keep the original root through Pause, login and Resume. Bind route selection before effects and prevent a later decline/error from handing partially executed research to an unrelated executor. The component currently has no host-routing caller.
2. Compile the proposal into semantic requirements and capability contracts. Resolve dates against the anchored clock, normalize amounts/currencies/counts, bind comparison direction and negation, distinguish alternatives from conjunctions, and preserve unknown or contradictory requirements for clarification. Source occurrence alone cannot establish any of these meanings. Do not hide unbound fields by treating `research` disposition as approval.
3. Build dynamic browser stages from that retained goal using observed targets and typed arguments. Connect navigation/search, supported form edits and queries, links, observation and scrolling with stable effect identities and existing journals. A successful stage satisfies only its own predicates; it cannot terminalize the research task. Add required custom-widget, JavaScript and POST semantics explicitly.
4. Compile candidate results with source text, actual container/link references and verified fact associations. A common ancestor may contain multiple offers or advertisements. Check date/place/count/price/fee/availability requirements, distinguish partial findings and unknowns, preserve cross-page provenance and qualify shareable URLs before returning a complete answer.
5. Implement typed intermediate clarification for the whole browser goal. Preserve original requirements and the fixed clock across scoped user answers, keep host questions separate from user-supplied values, and coordinate transport answer IDs with the stable browser root. Existing current-form clarification transfer cannot simply replace a multi-stage browser task's identity.
6. After later explicit permission, typecheck/build, qualify the model proposal and semantic compiler with independent cases, run controlled driver/receipt/handoff gates, and only then run bounded real-site travel/concert/movie scenarios. Keep holdouts unused until that qualification stage. Performance optimization remains after correctness repairs.

The overall browser research repair remains open. This component establishes retained proposal input and output, not a substitute for the missing semantic compiler, browser driver and result verifier.
