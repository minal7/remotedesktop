# Recovery after a browser answer is rejected

Source repair; execution pending. This follows the [answer-admission policy repair](BROWSER_ANSWER_ADMISSION_POLICY_REVIEW.md). No build, typecheck, test/assertion, app, browser, model, login or SSH run was performed.

Follow-up: the [live question replay repair](CLARIFICATION_LIVE_REPLAY_REVIEW.md) now checks normal browser/native text questions and retries after the outbound queue wait, before channel handoff. It also requires live native proof for older unclassified question records; process/session reconstruction remains open.

## First-principles findings

A submitted message and an accepted instruction are different events. If an answer exceeds the native conversation capacity or contains no usable text, it must not change the task's source, scope, clock or accepted-answer identity. Rejection also does not mean the original question disappeared. Previously, native admission retained that question but the manager sent a generic terminal failure telling the phone to start over.

Recovery must therefore describe two identities: the rejected attempt, which has completed without accepting an answer, and the original question, which can still receive a correction. Reusing the attempt ID for corrected text would violate the exact-body ledger fence. Issuing a new question would incorrectly renew its scope or expiry. Treating the rejected text as conversation context could change the meaning of the next instruction.

An old retry is not authority to recreate an owner. Native liveness, controller identity and exact question state must still hold when replaying it. Similarly, cancellation must be absorbing without letting an old rejected attempt cancel a newer accepted continuation. Historical association and permission to retry must be stored and projected separately.

## Implemented behavior

1. **Negotiate the optional contract.** The [shared protocol](../../../protocol/Swift/ComputerUseProtocol.swift) adds `supportsRetry` to the question's advisory answer policy. The phone advertises `supportsClarificationRetry` only on an answer to an advertising host. False values are omitted and missing values decode as false. The opaque reference is unchanged. Older clients and unnegotiated answers retain the generic failure path; this source repair does not retrofit their composers.
2. **Reject before native append.** The [browser clarification bridge](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserClarificationTransport.swift) checks the registry owner, controller/session, original reference, input digest, execution identity and current native question before applying byte/nonblank limits. A sealed `RejectedAnswer` contains a typed reason, current policy and the unchanged question. Rejection neither appends text nor advances the owner's execution ID. An accepted correction still passes the existing native answer operation.
3. **Persist the attempt separately.** The [host manager](../../../host-mac/RemoteDesktopHost/ComputerUse/HostComputerUseManager.swift) catches that rejection before selecting or invoking a continuation. It sends `clarificationRetry` only after the [task ledger](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseTaskLedger.swift) records the attempt's terminal result. The ledger requires an existing matching question owned by the same controller/session and an attempt with no approved-action record or plan. First-terminal-result behavior and exact wire-body claim identity remain intact. Malformed retry records cannot load as fresh work.
4. **Keep the admission fence intact.** The existing ledger flag `executionStarted` is set by `claim`, before request decoding or executor invocation. It is an admission/idempotency fence, not evidence that an executor actually ran. This repair does not clear or reinterpret that flag. The manager's ordering and authored continuation/planner counters specify the absence of execution for rejected answers.
5. **Gate every retry replay on live state.** A persisted retry must still match the actual submitted invalid body, negotiated capability, reason, native limits and exact live owner/question. Expired, paused, consumed, replaced or retired owners cannot yield an actionable retry. An unavailable retry becomes an inability response; the ledger cannot reconstruct a browser process or session.
6. **Preserve full question text.** Retry updates use the existing complete-question bound and carry the reason separately. Prefixing an error sentence could push a maximum-sized question beyond its cap. Retry metadata is valid only on an intervention outcome for a distinct answer-attempt ID and cannot coexist with a normal question, policy, action evidence, evidence-only flag or research progress. Existing transport frame checks still apply.
7. **Restore only the phone's own answer.** The [phone session model](../../../ios/RemoteDesktop/ComputerUse/ComputerUseSessionModel.swift) requires an active matching attempt, the selected host/pairing/session, an exact submitted question reference, negotiated capability and a policy that actually rejects the submitted text for the supplied reason. Status-only retries, stale attempts and pending Pause/Cancel cannot reopen the composer. Existing control epoch/revision and approval checks still apply.
8. **Keep the draft and deadline.** The [pending prompt store](../../../ios/RemoteDesktop/ComputerUse/ComputerUsePendingPromptStore.swift) retains the original local question deadline with a negotiated answer, including pairing-code rebinding. Retry uses that deadline rather than another ten-minute allowance. Missing, nonfinite or extended deadlines cannot restore a question; an elapsed valid deadline produces the expired-answer state. A live recovery exposes the exact rejected draft and installs the returned policy. The [view](../../../ios/RemoteDesktop/ComputerUse/ComputerUseView.swift) fills an empty composer without overwriting another draft. Corrected submission uses a new attempt ID, the original reference and no reconstructed chat history.
9. **Propagate cancellation precisely.** Cancel after rejection retains the historical question association in the ledger but withholds public retry metadata. It retires only the matching pending native question and cancels a durable question only when its stored reference still matches. Cancel preceding the prompt is reconciled after the prompt's exact body is bound. Repeating Cancel can finish historical question cleanup after a partial storage failure/recovery; a poisoned live ledger still rejects work until recovery. Foreign nonces and stale references cannot cancel a different durable question. An old cancelled attempt does not retire a newer accepted owner execution.
