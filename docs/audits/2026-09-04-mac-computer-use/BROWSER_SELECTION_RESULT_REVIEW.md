# Keep selected settings separate from result facts

Source checkpoint, 2026-09-08. Previous checkpoint: `f646d0e`. Execution remains deferred.

## First-principles defect

The preceding control-state repair established what a control currently shows and whether that observation has changed. It did not establish that a provider had applied the setting to its results. Its date fixture could complete using only a matching date control, title and price. A positive semantic review could also cite a selected location, time or availability option as the result fact that fulfilled a requirement.

Freshness and causality are different questions. A date picker can show September 20 while an older result still says September 19. Re-reading that picker confirms the chosen setting; it does not confirm a September 20 result. The fix must retain both observations, require result evidence separately, and preserve contradictions rather than replacing one value with the other.

## Source changes

- [Candidate fields](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultCandidates.swift) now derive `source_kind` from their already admitted references: `pageText`, `controlState` or `mixed`. `result_support_allowed` is true only for a nonempty text field with no control references. Neither value is accepted from model output. Mixing a control reference with some page text cannot erase its provenance. Current planning and historical recall retain these distinctions.
- [Native review admission](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultReview.swift) now requires a positive requirement judgment to cite at least one complete offer-scoped, relevant field that permits result support. Control observations can remain context, qualifiers or conflict evidence. They cannot supply the required positive result fact. An `unknown` judgment remains valid so the driver can seek more evidence. Exact offer prices require the same text provenance; selected prices cannot become exact prices. The existing separate prohibition on control-sourced available inventory remains in place.
- Scope `offer` on a control continues to mean a proposed association with that candidate. It does not mean the setting has been accepted or its outcome observed. [Review instructions](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultReviewPlanner.swift) explain this distinction and the native provenance flags. Review context/schema advances to version 5 when control sources are offered; segmented review uses `browser_result_review_part_v4`. Final assembly applies the same native checks as a whole response.
- [Scalar assessment](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultAssessment.swift) retains text IDs and control IDs separately. Each scalar record carries its source kind. For date/price requirements, selected fields are checked separately from result text: every proposed applicable selection must have a complete comparable value and agree with the requirement. A conflicting selection produces `selectedValueConflicts`; mixed/unparsed and incompatible selected values remain unresolved.
- Matching selections without a result field produce `needsResultObservation`. Result text is then checked independently using the existing complete-literal, association, price-qualification and ambiguity rules. A stale result date cannot inherit the chosen date. Several consistent control observations no longer masquerade as several competing result dates, while a conflicting control cannot disappear behind a matching result. The existing quantity-meaning path remains separate.
- [The link planner](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserLinkPlanner.swift) receives the provenance and unresolved statuses, with instructions to seek result/detail evidence. Existing answer eligibility admits none of the new unresolved statuses. The original request, accepted answers, control context, history and login handback rules remain intact. No navigation is inferred merely from a matching control.

This establishes an additional necessary evidence boundary. It does not prove that arbitrary text is genuinely a provider result, that a provider honored every filter, or that stock remains available. The model still proposes whether text belongs to one offer and whether a setting applies to it. A caption echoing a filter can still be misclassified as a result by an unqualified model. Provider-specific result/selection relationships, time-zone and quantity semantics, asynchronous refresh and full offer verification remain open.
