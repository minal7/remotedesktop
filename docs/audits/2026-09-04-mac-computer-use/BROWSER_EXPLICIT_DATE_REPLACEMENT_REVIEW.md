# Explicit replacement of one date requirement

Source repair; execution pending. This follows the [introduced date origin repair](BROWSER_INTRODUCED_DATE_ORIGIN_REVIEW.md). No build, typecheck, assertion, app, browser, model or account-login execution occurred.

## First-principles contract

Confirming a value, replacing a requirement and proving a browser effect are separate events. A later literal date does not, by itself, authorize erasing an earlier date. Conversely, retaining every old date as simultaneously active makes an explicit correction impossible. Deleting old text would also destroy the explanation for earlier searches, field values and receipts.

This repair adds an explicit user decision about one known date origin. It retains the original request, clock, every answer and all earlier effects. The active date moves to the replacement answer's own source rows. Old date obligations become linked history; they cannot supply new action arguments. Other requirements remain active.

## Visible replacement decision

The [clarification boundary](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserGoalClarification.swift) has a separate `replaceDate` topic. Its fixed question tells the user that their answer will replace the whole selected date requirement, including its weekday or before/after limit, while other requirements stay in place. Ordinary `date` answers retain the existing confirmation/disambiguation rules.

Admission requires one native date origin. A broad missing outcome, arbitrary date-labelled text, a partial date/range or two independent trip/event dates cannot qualify. A recognized conflicting literal retains its original target so the user can explicitly resolve that conflict. Compound answers do not gain that lineage.

The model's selected row is not necessarily the date being replaced. A confirmation or conflicting answer may point back to an earlier clause. Before installing a replacement question, the host resolves and canonicalizes its scope to that actual origin. The displayed source and accepted answer scope therefore identify the original date requirement, not merely the later literal selected by the model. Complete source groups must still fit the existing eight-reference limit; no origin is truncated to fit.

[Goal, action and form question admission](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserGoalPlanner.swift) use the same native rule. Proposing a replacement question changes nothing. Only consumption of its live, authenticated question creates the accepted replacement turn. Existing controller/session binding, expiry, answer-ID handling, complete source coverage and root ancestry remain required. Known date origins cannot become quantity questions through a new model label.

Instructions tell planners to use replacement for a requested correction or conflicting user dates, not to relax a requirement to fit website results. This is an explicit question/answer path, not general unsolicited-prompt steering or arbitrary semantic reclassification.

## Retained date graph

The [native scalar ledger](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserScalarRequirements.swift) distinguishes bound dates, ordinary clarification bindings, unresolved dates and superseded date obligations. A successful replacement binds its own full answer group to the new date/range, or retains a weekday as unresolved native date meaning. An unresolved weekday still needs its compatible civil date before exact normalization.

Every retired source remains an entry linked to the replacement. Successive replacements preserve a graph rather than flattening away branches. If one prior confirmation covered two dates, replacing one date retains that answer's application to the other. When both applications are eventually replaced, the old answer retains references to both date branches and the corresponding replacement turns.

An ordinary conflict remains unresolved until the user explicitly replaces the selected origin. Invalid calendar values, malformed scopes and compound replacement answers cannot retire a date. Unrelated instructions in an uncompiled answer are not discarded. If an accepted replacement cannot be reconstructed under the current interpretation, new task-purpose payloads and form queries remain unavailable; the old date does not silently regain authority.

The original source still can be recorded and read as history. The source-record type does not itself grant an action. New-purpose checks live at the query, choice, field-intent, preservation, popup and option boundaries. A partly superseded shared answer also cannot supply a new ambiguous payload; its still-active date origin provides the usable source.

## Remaining repair sequence

1. Generalize explicit user correction beyond a native date origin: locations, quantities, budgets, source policies and mistaken semantic classifications need their own well-scoped replacement and dependency rules. Do not infer replacement from the latest text alone.
2. Reconcile arbitrary source merging/splitting, multiple trip-leg/provider roles and conditional or negated clauses. Historical root-date repartitions that no longer identify one native unit remain uncompiled; they are not permission to erase modifiers.
3. Extend native reconciliation for dropdown/selection histories, cross-document/account changes, preservation/read duties and uncertain effects. This repair does not discard those histories to make a date correction proceed.
4. Support longer retained conversations and direct user steering without truncating previous requirements. The existing four-user-turn and eight-scope-reference limits remain. The original task clock is retained; later relative-date answers need an explicit policy for their time origin and how that context is explained to the user.
5. Qualify the authored cases, then the deferred real travel/concert/movie and login-handoff scenarios at the explicitly authorized stage. Review model competence, task success and resource behavior independently; changing the requirement graph is not model or 8 GB Mac qualification.
