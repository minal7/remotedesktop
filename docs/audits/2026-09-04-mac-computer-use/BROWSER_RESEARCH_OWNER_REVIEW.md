# Retain one browser research task through planning and user control

Date: 2026-09-07. Parent source: 55349f0. This checkpoint adds a canonical research owner, an explicit host preparation entry and host lifecycle handling. **General natural-language research routing, action planning and complete research answers remain unfinished.**

## First-principles finding

Separate correct components do not establish a correct task. A result reader can validate a supplied goal while its caller supplies an obsolete revision. A clarification can preserve the original request while another component rebuilds “tomorrow” from a later clock. Cancellation can reject a late answer while a second operation has already started. A login redirect can preserve the account session while invalidating the old page and its targets.

The missing common authority was one retained owner of the original goal, its clarification revisions, the actual browser session and the currently outstanding operation. This change provides that owner for interpretation and result reading. It does not treat a model's research classification, parsed scalar condition or source-bound candidate as proof that the whole request has been understood or satisfied.

## Implemented behavior

1. `ComputerUseBrowserResearchTask` owns one `ComputerUseBrowserGoalClarification` instance and derives its current input from that instance. The original task ID, request bytes, reference time and time zone survive interpretation, question answers and explicit handback. Callers cannot supply an older goal to this owner's candidate validation API.
2. Goal interpretation retains the complete proposal and scalar ledger for the current revision. Foreign proposals are rejected. Repeated access reuses the current interpretation. If this task already owns a browser page, the owner observes that page before new inference to detect visible authentication or control loss. Interpretation never claims a browser, opens a website or creates an effect journal.
3. Candidate reading requires a current research proposal and this task's actual owned page. The owner acquires and observes that page, passes the complete current goal to the result planner and prepares the proposal against retained native evidence. It checks cancellation, control, the canonical revision and session identity around the asynchronous work. The model still selects source references; it does not authorize actions or certify offer semantics.
4. Candidate revalidation uses the owner's canonical input and retained native evidence. A failed validation clears the previous cache before returning the error. A successful revalidation is a fresh check of the retained reading, not proof of availability, price interpretation or whole-goal completion. Reading a new page replaces the cache; cross-page collection is not implemented here.
5. Questions use the existing typed topics, exact requirement references, expiry and bounded answer history. The browser part of their context comes from the owner's actual session, rather than a caller-supplied browser digest. Controller and controller-session IDs still must come from authenticated host transport. Answers clear both interpretation and candidate caches; old question references cannot change the new revision. Expiry observed through answer or pending-question access clears the owner's pending flag. There is no background expiry poller.
6. One operation slot covers goal inference, result reading, revalidation and handback. Parent cancellation propagates to the child, but the slot remains occupied until that child actually finishes. Pause or retirement also cancels the child. A cancellation-ignoring callback cannot free the slot early or publish a late interpretation/result. Control epochs prevent an older operation from succeeding across another Pause.
7. Pause immediately clears candidate readings and invalidates unanswered questions while retaining the canonical input and its current interpretation. It seals the original browser session for handback without closing the page the person is using. Explicit Resume requires the prior operation to have unwound and the host action gate to allow work. It reacquires the same session, observes the current page and checks authentication before unpausing. The same session may have changed pages during login; a closed or replaced browser cannot be substituted. A task paused before acquiring any browser cannot silently adopt a browser that appeared during the pause.
8. Retirement is permanent for that owner. It clears interpretation, readings and questions and cancels outstanding work without releasing its slot prematurely. Restoring the action gate cannot revive the owner. Preparing the same root again returns the retained owner and original clock, including its retired state. A valid different root replaces and retires the previous owner; invalid preparation does not discard a valid retained task.
9. `ComputerUseBrowserNavigationTask` retains the research owner beside the existing explicit workflow. It retires the owner on browser Stop/Close and when explicit navigation/workflow execution changes to another root. Preparing research does not run either planner or dispatch navigation. It provides no authority for dynamic action steps; those still need whole-goal contracts and journals.
10. `ComputerUseHostTools.prepareOwnedBrowserResearch` provides an explicit preparation entry using the existing owned-browser facade and action gate. Host Pause forwards to the retained owner. Explicit host Resume joins prior execution, performs the existing browser handback and then resumes the research owner. Stop and disconnect retire it. Terminal host replies also retire the matching owner, including the failure path when terminal persistence fails. Existing legacy text-clarification terminal replies therefore cannot serve as the future resumable browser-question transport.

The host entry is available for a future research driver. The ordinary capability route still recognizes only the existing complete explicit browser workflows/navigation before its other executors. This checkpoint does not send arbitrary research requests into the new owner, publish research questions to the phone or generate research answers. No new model worker, timer or performance optimization is introduced.

## Remaining repairs in dependency order

1. **Compile the complete meaning of the goal and its answers.** Source coverage alone does not establish meaning. Resolve negation, alternatives, location/route roles, dates and time zones, party size versus requested result count, price basis/currency/fees, availability and sorting. An answer must resolve or explicitly replace the intended requirement without silently dropping another condition. Keep all unresolved requirements visible to subsequent planning.
2. **Connect the owner to an actual research route.** Create it from the original authenticated request exactly once. Pass the complete retained input and remaining obligations to the planner. Define a bounded next-step proposal with host-validated targets, payload sources, prerequisites and expected outcomes. Unknown whole-goal meaning must not cause an explicit supported prefix to run as if it covered the request.
3. **Integrate browser questions with the host and phone.** Bind question presentation and answers to the authenticated controller/session, original root and current goal revision. Preserve exact answer bytes and durable replay behavior. Map Pause/Resume/Stop to that root even when an answer has a separate transport message ID. Retire references on expiry, disconnect, controller changes and replacement. Do not reuse the legacy terminal text-clarification path, which ends the prepared owner.
4. **Connect dynamic steps to retained effect journals.** Reuse the existing native form edits, queries, observed links and scrolling only after each proposed step is authorized by the complete goal. Preserve stable occurrence identities and attempted/verified/uncertain states through replanning and answers. A new revision, login redirect or changed target cannot authorize repeating an effect whose outcome is uncertain.
5. **Verify source-associated offer facts.** Establish which title, place/route, date/time, quantity, price, fees and availability belong to the same offer. A common container can hold multiple offers or prices. Retain and interpret unclassified and global context before constructing scalar observations. Exact arithmetic cannot repair a wrong association.
6. **Retain cross-page findings and publish suitable sources.** Track observation time, provenance, duplicate offers and freshness independently of DOM candidate IDs. Define when earlier findings are historical or must be revisited. Qualify public result links separately from private navigation/query/account URLs. Missing or omitted records cannot prove no matches or an exhausted search.
7. **Prove and present the full answer.** Require each requested outcome and condition, with explicit partial or unknown results where evidence is missing. Recheck relevant page/session evidence at publication. A model stop, successful navigation, current DOM binding or satisfied numeric comparison proves only that narrower operation.
8. **Qualify after explicit permission.** First typecheck/build and run independent controlled cases covering host, phone, browser, model, journal and login composition. Then use the retained bounded travel/concert/movie website scenarios. Keep holdouts unused until qualification. Resource and 8 GB/thermal optimization remain in the later performance phase.
