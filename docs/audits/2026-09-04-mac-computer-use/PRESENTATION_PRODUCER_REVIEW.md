# Native presentation producer candidate

Source preparation, 2026-09-10. This continues [native surface isolation](NATIVE_SURFACE_LIFETIME_REVIEW.md). No builds, typechecks, assertions, native image/GPU operations, app launches, browser actions or model inference were executed. The producer is **not instantiated by the app**. Existing renderer selection and submission-based readiness are unchanged; this component does not close the presentation or natural-language acceptance gates.

## First-principles boundary

A returned `renderFrame` call says that a sink accepted a call. A command-buffer completion says that GPU work finished. Neither identifies the frame actually presented. The needed local chain is: retain a decoded frame, encode its image into a known drawable, present that same drawable, observe successful GPU completion and a positive native presentation time, then check that the owning surface/layout is still current. Even that chain does not prove when the host captured those pixels or that another view did not cover them.

The [previous source review](RENDERER_OWNERSHIP_REVIEW.md) replaced the parallel probe, and surface isolation removed shared native state between attachments. The public WebRTC view API still does not expose a drawable receipt. The next producer therefore uses public Core Image and Metal APIs directly rather than introspecting private WebRTC view fields.

The inspected Apple SDK [drawable API](https://developer.apple.com/documentation/metal/mtldrawable/addpresentedhandler(_:)) defines a callback for presentation and reports zero presentation time for unpresented/skipped frames. The [Core Image destination API](https://developer.apple.com/documentation/coreimage/cirenderdestination) accepts a specific Metal texture and command buffer, with explicit orientation and color-space properties. [Apple's Core Image/Metal example](https://developer.apple.com/videos/play/wwdc2022/10114/) shows the render-task and drawable workflow. These APIs support preparing this implementation; they are not native qualification results for this code.

## Implemented candidate

[RemoteVideoPresentationProducer](../../../ios/RemoteDesktop/Transport/RemoteVideoPresentationProducer.swift) owns one Metal layer, command queue and Core Image context. It accepts only a fresh drawable from that exact layer/device, validates texture format and bounded dimensions, and refuses reused/non-increasing drawable IDs. Within a context, drawable size and content mode remain fixed. The caller must explicitly replace context for changed layout, activity or visibility. A receipt also rechecks the layer's current drawable size and ignores older results after a newer presentation.

For CVPixelBuffer-backed decoded frames, the producer retains the input through actual GPU completion. It uses the wrapper's crop rectangle, converts its top-left origin into Core Image's lower-left coordinates, crops before applying adaptation scale, then applies frame rotation. It supports the wrapper's NV12 full/video-range, BGRA and ARGB formats through Core Image. It composes a bounded opaque output, using fill for the full-display surface or aspect fit for legacy mapping. The destination explicitly uses top-left texture storage and sRGB output. Real color attachment handling, alpha, crop, rotation, scaling and pixel fidelity remain untested.

The image is encoded into the exact supplied drawable texture through `CIRenderDestination` and the same explicit command buffer later used to present it. The producer attaches both GPU-completion and drawable-presentation handlers before committing. Immutable local ticket/frame/context identities and the actual drawable object/ID travel through those callbacks. The native callback retains source/Core Image resources until GPU completion, independently of observer lifetime. There is no screenshot, private KVC access, nil-frame clearing assumption or source-capture timestamp fabrication.

[RemoteVideoPresentationLedger](../../../ios/RemoteDesktop/Transport/RemoteVideoPresentationLedger.swift) tracks at most two reserved operations in the shared production budget. Its state distinguishes reserved, committed, GPU-completed, presented, retired and expired work. Successful GPU completion plus a positive finite presentation time produces a receipt; either arrival order works. Skipped/nonfinite/nonpositive presentation cannot succeed. A GPU failure cannot be overwritten by a later callback. Wrong drawable object/ID, retired ticket and duplicate callbacks are ignored.

Retirement suppresses callbacks immediately but keeps committed unfinished work charged. A provisional five-second observation deadline reports expiry once; it does not cancel or free unfinished GPU work. Completed work waiting for presentation can be freed on explicit retirement/expiry because GPU completion has actually been observed. Uncommitted preparation can be abandoned without manufacturing a native completion. Bookkeeping and deadline callbacks are removed before external delivery to tolerate reentrant caller changes.

## Explicit limitations and activation blockers

1. **Visibility/input integration is unfinished.** The current screen uses opaque waiting overlays while input is unavailable. A producer waiting for visible presentation cannot simply replace the old callback under that overlay. Separate permission to reveal candidate pixels from permission to send input; preserve opaque account/activity/login privacy shielding. Surface layout, window, viewport/zoom, activity and privacy changes must retire/rearm the presentation context. The backend's size check alone cannot observe all those events or occlusion.
2. **Format coverage is incomplete.** Non-CVPixelBuffer frames are rejected by this candidate. A generic `toI420()` fallback loses information needed to choose color/range behavior, and some conversions can copy/scale large buffers. The [M144 CV wrapper reference](https://raw.githubusercontent.com/webrtc-sdk/webrtc/30d5e63ae91da483e06577b5c35ee91cc5e5c3db/sdk/objc/components/video_frame_buffer/RTCCVPixelBuffer.mm) handles NV12/BGRA/ARGB adaptation, while the [I420 renderer reference](https://raw.githubusercontent.com/webrtc-sdk/webrtc/30d5e63ae91da483e06577b5c35ee91cc5e5c3db/sdk/objc/components/renderer/metal/RTCMTLI420Renderer.mm) uses its own color conversion. Neither establishes the installed binary's exact behavior. Complete explicit planar/color handling and negotiated format qualification before replacing the current renderer; unsupported software-codec frames must not silently become black successful output.
3. **Caller ownership and failure policy are incomplete.** The future surface must own drawable acquisition, one bounded latest-frame mailbox, context changes, retirement, availability callbacks and bounded retries/deadlines when no drawable or budget is available. The candidate does not acquire drawables or drive a display loop. `.busy`, `.unsupportedFrame`, `.unavailable` and `.encodingFailed` are distinct admission results requiring caller handling. Do not retry an already committed drawable.
4. **This is a local rendering association, not end-to-end pixel provenance.** Keeping a decoded frame alive is necessary, but decoder-buffer immutability/reuse and actual output must be qualified. A new context can still receive an old queued decode. Carry capture identity through adaptation/codec/transport and maintain the [fresh-image recovery constraints](CAPTURE_FRESH_IMAGE_DESIGN_REVIEW.md).
5. **Native execution and resource behavior are unqualified.** Core Image may compile kernels or use intermediate buffers; the two-slot/five-second settings are provisional limits, not measured memory or responsiveness budgets. Native completion that never arrives holds its permit. Destination preflight cannot prevent earlier oversized decoder/drawable allocation by the caller. No 8 GB or thermal claim follows. Actual GPU failure, skipped presentation, layering, backgrounding, retirement, source retention and callback timing need controlled native evidence.
