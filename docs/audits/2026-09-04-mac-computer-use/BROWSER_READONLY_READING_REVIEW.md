# Read displayed criteria without granting edit authority

Source checkpoint, 2026-09-08. Previous checkpoint: `77fa670`. Execution remains deferred.

## First-principles defect

Read-only and disabled describe how a control can be operated, not whether it displays a value. The prior research reader correctly refused edits to these controls but also excluded all their values. The scoped reader inherited that restriction. A read-only departure date or location could therefore remain unavailable even when needed to assess a result. The [unread-control relevance review](BROWSER_CONTROL_RELEVANCE_REVIEW.md) could identify that dependency, but could not resolve it without pretending it was unrelated.

Reading a displayed setting needs its own bounded task scope. That scope must not change interactivity, authorize editing, establish that the provider applied the setting or imply that an unavailable choice is bookable. The same separation applies to a selected option inside a disabled selector and to a checked disabled checkbox.

Native scalar/text values remain whole and bounded; selected option identities retain complete labels and group context, and checked/indeterminate flags remain exact. Option submission codes are excluded. No input property, disabled flag, read-only flag, selection, focus or form is changed by collection.
- The internal observation member is now `scopedControlIDs`, reflecting that the scope can include non-text native state. Its bound remains sixteen unique eligible controls. [State validation](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserControlState.swift) distinguishes a well-formed value from authority to admit it: the complete snapshot separately requires scope membership for every text state and every read-only/disabled value-bearing state. A plausible typed state cannot bypass a missing, partial, duplicate or foreign scope. Ordinary observation clears that scope.
- Validation re-reads the same native state and flags. Property-only value, selected-index or checked-state changes invalidate a reading even without an input event. Changing read-only/disabled status also changes the evidence. The next fresh observation can use ordinary reading if the control becomes an ordinary enabled scalar; an old scope cannot be carried through that change.

This extends the existing action decision, not a separate inference stage. Pages with newly eligible controls can now require that bounded decision. Existing editable-form discovery still excludes read-only/disabled controls. The native reader, current result input and owned-browser checks use the generalized scope name together; these are internal in-memory observations, not a migration of installed app state or persisted task records.
- Result and review prompts preserve interactivity flags and distinguish observed settings from provider result facts. Existing source provenance still forbids control-only positive result support and exact offer prices. A matching read-only date does not fill in a missing displayed result date or replace a conflicting one. Existing owner cancellation, Pause, explicit login handback, fresh scope selection and DOM completion joining remain in force.
