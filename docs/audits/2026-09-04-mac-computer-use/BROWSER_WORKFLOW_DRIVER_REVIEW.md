# Connect explicit browsing stages under one task

Date: 2026-09-07. Parent source: `848bdfd`. Source integration only. Builds, typechecking, test execution, model runs, app launches and computer-use activity remain paused.

## First-principles defect

A user's request is larger than a tool call. Opening the first page, filling a form, loading a query and opening a selected result are intermediate actions with different evidence. Giving each action a replacement top-level task loses the original goal and login ownership. Treating a successful form edit as whole-task completion loses everything after the edit. Reconstructing completed actions from a new page can also repeat a request that already reached the website.

The source had complete URL-only and form-only execution paths, plus observed link/query capabilities that were not connected by the normal host route. A broad visual loop could not substitute for the missing stage graph, exact form requirements or durable navigation records. This repair adds the deterministic entrance to a browser driver and connects it to the host. It does **not** claim to interpret or complete general travel, concert or movie research.

## Source integration

1. `ComputerUseBrowserWorkflowRequest` consumes the entire explicit request before any page opening or input. It recognizes existing complete URL-navigation clauses, existing quoted form commands, explicit link openings and explicit native form-query openings. Quote-aware `then` boundaries preserve literal bytes inside quotations. Adjacent form clauses stay together so copies, previous-field references, invariants and repetitions retain the existing complete-form semantics. Unsupported suffixes decline the entire workflow and leave the original request available to the broader route.
2. The request is sealed by a private initializer. It retains the original prompt, ordered clause sources and capability kinds, bounded to 32 KiB and 16 stages. It is not model-authored JSON. URL-only and form-only requests continue through their existing complete capabilities. The query spelling is deliberately explicit (`open the form query using "Search"`): a native GET-query opening cannot silently redefine a requested DOM click, POST or JavaScript submission.
3. The production host's owned-browser route selects the complete compiled workflow before form/desktop fallback. A selected workflow keeps the same root task and the exact original prompt. It does not launch another task per stage, pass partial success to the host as a terminal result, or fall through to another planner after a child starts.
4. The owned browser allocates a session identity without opening a URL or posting input. The parent journal binds that browser lifetime/ownership, the root prompt digest and the complete ordered stage IDs. Existing-page workflows acquire the current document through the usual ownership/observation boundary. A changed goal, replacement browser or recreated WebView cannot bind a fresh operation to the old task record.
5. The parent record lives in `Workflows`, with isolated child records under each stable stage ID. It stores hashes, IDs and statuses, not URLs, form values, passwords or the prompt. Compare-and-advance persistence and an execution lease cover each full run, including asynchronous child execution and cancellation unwind.
6. A parent `attempted` status records **delegation**, not proof that an input occurred. It resumes the same child capability and its own durable record. Only the child can reconcile its individual effects. Navigation uses native document receipts; form edits use retained contracts, exact snapshots and independent input receipts; observed destinations use their durable no-replay facade. The parent marks a stage verified only after that child succeeds. Verified earlier stages are skipped.
7. Navigation children now receive a stage namespace. Two deliberate visits to the same URL produce distinct native effect identities, while a retry of either visit keeps its original identity. Existing standalone navigation identities remain unchanged. Parent stage IDs also bind the original prompt, ordinal, kind and source, so retry never invents a new ID to evade uncertainty.
8. Future form fields and links are resolved only when their page is current. Form children use the existing complete quoted-command compiler and no additional planner. Their provider always supplies the owned browser or throws; it cannot switch to AX on an unrelated app. Displayed-browser targets retain foreground checks, while explicitly headless fixtures remain available for later controlled verification.
9. Link/query labels must resolve uniquely in fresh page evidence. A query immediately following a form stage uses that exact retained executor's verified continuation, including intended final values, unchanged fields and each input receipt. A manual value change cannot become a replacement query under the old instruction. The observed-destination journal receives the full root prompt digest and stable stage ID.
10. Authentication propagates to the existing visible handoff and explicit Resume path. A pre-edit login can complete in the same browser session, refresh the document, and resume the pending form without repeating the initial navigation. Possible child effects remain governed by their journals. Missing/ambiguous form references ask for a manual page correction while retaining the original request; stale or uncertain effects do not authorize fallback.
11. A terminal result requires every compiled stage to be verified, a current presented document and fresh page observation. It reports the bounded page-opening/form-edit work. It does not claim that tickets were found, dates/prices matched, authentication succeeded, results were exhaustive or a transaction completed.

The new source is registered in the Xcode app target. `project.yml` and SwiftPM already include its source directory.

## Remaining repair order

1. Add the semantic whole-goal compiler for normal research requests. Retain requested entities, dates, places, counts, limits and comparisons as explicit requirements. Do not make users spell out this deterministic stage language or describe the primitive driver as general natural-language understanding.
2. Extend the driver with reviewed semantic stage bindings and complete outcome predicates. Each derived intermediate action needs goal/argument/target authority; page labels and source-span occurrence alone are insufficient. Broader date/location interpretation, generated search text and dynamic choices remain unimplemented here.
3. Verify complete travel/concert/movie results with correct fact associations, current source pages, availability, prices/fees and selected shareable links. An HTTP response, visible line or completed input is not a complete research result. Bound multi-page accumulation and repeated-state recovery.
4. Implement the site-required POST, JavaScript, custom-widget and additional-context capabilities separately. Native GET-query navigation deliberately does not dispatch click/submit events. Real ticket sites cannot be assumed to support this primitive.
5. Reconcile partially edited forms after document replacement and recover durable remaining-goal state after host/browser loss. This driver retains child adapters within the live session; missing adapter authority or old uncertain effects still block. It does not reconstruct account sessions, restore private DOM references, recover from arbitrary journal deletion or establish server-side outcomes after loss.
6. Complete typed clarification/approval steps within a multi-stage task, including phone history and account verification without credentials. The deterministic driver currently includes neither generated drafts nor consequential approved operations. A manual page correction is not a general text-answer continuation protocol.
7. After later explicit permission, typecheck/build and run the controlled gates before the agreed bounded real-site scenarios. Keep holdouts unused.
