# Preserve a browser goal across typed clarification answers

Date: 2026-09-07. Parent source: `3d2fc89`. Source changes to the browser goal input, planner contract and an in-memory clarification owner. **Host/phone presentation and general browser research routing are still unconnected.**

## First-principles finding

The existing form clarification route transfers native execution to an answer's transport task ID. That is not sufficient for browser research that has already visited pages or handed control to the user for login. The answer is a new input to the original goal; changing the browser root could detach its session, completed stages and effect receipts. Conversely, treating the latest answer as a replacement prompt loses earlier requirements. Joining a generated question with an answer creates another error: host wording can become apparent user instructions or supplied values.

Browser clarification therefore needs separate identities for the retained root, the current input revision, the pending question and the answer transport message. It also needs complete source coverage across user turns, a question scope, bounded lifetime, and explicit integration with existing ownership and journal rules. This change supplies the input/question boundaries and connects structured clarified input to the existing proposal planner. It does not establish the missing driver or UI integration.

## Implemented behavior

1. `ComputerUseBrowserGoalInput` now retains an immutable original prompt, task ID, reference milliseconds, time zone and `rootDigest`, plus ordered typed clarification turns. Accepted answers change only the input revision digest. The root digest and clock are copied directly; they are not reconstructed from a new time, normalized prompt or transport answer ID.
2. A clarification turn holds the exact answer bytes and transport ID, the prior input revision, question identity, typed topic and source scope. Up to four user turns are retained, with 8 KiB per answer and 32 KiB across user input. Blank, oversized, repeated-ID, root-ID or foreign-revision answers cannot be appended. These input bounds do not guarantee that a complete proposal will fit the stricter token/output limits.
3. `ComputerUseBrowserGoalClarification` is one MainActor-owned in-memory state holder. A question requires the current proposal revision, a supported disposition, one to eight unique known requirement IDs and a compatible host-selected topic. Scope is kept in original source order. Model roles/fields still supply interpretation only; these structural checks do not prove the question is semantically necessary or sufficient.
4. The host selects from fixed questions for origin, destination, location, date, time, quantity, currency, price basis or fees. The model's arbitrary proposed question string is never used as the displayed text by this boundary. Authentication has no question topic; it remains visible manual takeover. This code does not collect account credentials or read browser/account observations.
5. Each question binds a fresh nonce, input revision, original task, topic, source occurrences, controller/session context and a ten-minute expiry. The context distinguishes an explicitly absent pre-browser session from a supplied browser session digest. A different controller, controller session or browser binding cannot consume or retrieve the question.
6. Consumption is synchronous under MainActor isolation and validates question identity, revision, context, expiry and the whole new input before changing state. A successful answer consumes the reference once. Invalid answer contents leave it available for correction. Replay, recreation of the state holder, stale proposals, explicit invalidation, expiry and retirement cannot recreate that authority. No background polling or timer is added; expiry is enforced when the question is accessed, issued or consumed.
7. Question invalidation preserves the original goal and accepted answers. Stop/replacement can retire the state holder permanently. These methods are available for future lifecycle integration; they have no host lifecycle caller yet. The type itself cannot prove authenticated controller context or live browser ownership, and it does not validate successful login.
8. The proposal contract is now `browser_goal_proposal_v2`. Every requirement has an integer `turn` indexing original request 0 or a retained answer. Sources must cover each complete user turn separately, in order, byte-for-byte; offsets are relative to that turn. Missing original requests, missing answers, reordering, out-of-range/fractional/Boolean turn indices, Unicode normalization and sources or hints borrowed from another turn are rejected. Requirement and proposal identities use version 2 domains.
9. The model receives the exact original request, separate answer objects, fixed original date context, and typed host question/topic/scope context. Scope contains the original turn, byte offset and source fragment. Transport IDs, question IDs, controller IDs, root/revision digests and requirement IDs are omitted. Host question/scope text is never a source for user-turn coverage. Instructions explicitly retain contradictions and changes of intent for later semantic compilation.
10. The same existing local planner and runtime entry point accept the expanded input. Complete structured input is counted once and never shortened to fit. Existing cancellation, output admission, response integrity and model ownership checks remain in force. This changes the unqualified browser prompt/schema; it does not change model installation, process lifetime, served alias or qualified native-form behavior.
11. Scalar compilation now gets exact source fragments from their own user turn through the proposal's source accessor. Earlier prices and dates remain alongside later conflicting conditions. Reinterpreting a retained relative date uses the original clock. Whether a later answer clarifies, contradicts or replaces a constraint remains a whole-goal semantic decision; successful local scalar parsing cannot make that decision.

Default descriptions for input, question, turn, context and source scope omit user answer/source contents. The transcript stays in memory. This change does not add durable conversation storage, browser restart recovery or arbitrary log sanitization.

## Remaining integration and repair sequence

1. Compile whole-goal logic and associations. Use the typed question topic and source scope to interpret answers without treating them as unconditional replacements. Resolve origin/destination/location, date/time roles, count versus party size, price/fee/currency scope, alternatives, negation, availability and sorting. Keep unbound or contradictory requirements explicit.
2. Add the actual browser research owner/driver and host route. Retain this input and clarification owner under the original root through navigation, Pause, login and Resume. A stale proposal must be rejected against the current revision before preparing actions. A clarified input cannot be handed to an unrelated fallback executor after browser effects have started.
3. Integrate host/phone clarification transport separately from current-form identity transfer. Claim the answer's stable transport ID in the durable ledger before consuming the question, deduplicate retries there, authenticate the controller and derive current browser session context at the boundary. Do not use transcript text or a client-supplied digest as proof of ownership. Present the typed host question with a scoped reference and retire it on expiry, replacement, session loss and Stop. No wire/UI change has been made here.
4. Coordinate question invalidation with login takeover and explicit handback. The clarification context binds the browser session, not a stale document, so legitimate manual login redirects need not reset the goal. Actual ownership, authentication detection, fresh observations and target revalidation remain the existing browser boundaries' responsibility. Answering a task-detail question cannot itself hand control back or assert login success.
5. Preserve stage/effect history across input revisions. Do not derive replacement effect IDs from the latest answer and replay completed work. Reconcile attempted effects from receipts; only truly unattempted work may be rebound through the existing journal rules. A changed goal revision alone does not authorize replacing a persisted contract.
6. Implement source-associated candidate results and full completion checks, then qualify the complete model/driver/result/handoff composition after explicit execution permission. Real travel, concert and movie scenarios remain deferred, and holdouts remain unused. Performance qualification still follows correctness repairs.

The overall browser repair remains open. Root retention and scoped clarification are necessary components; they do not yet provide end-to-end natural-language browsing.
