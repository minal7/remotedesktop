# Recover a saved phone question through a fresh native check

Source repair; execution pending. This builds on [live question replay](CLARIFICATION_LIVE_REPLAY_REVIEW.md) and [rejected-answer recovery](BROWSER_REJECTED_ANSWER_RECOVERY_REVIEW.md). No build, typecheck, assertion/test run, browser/app launch, model invocation, account login or SSH attempt occurred.

## First-principles findings

The phone previously removed its recovery record when an explicit question arrived. The composer retained the reference only in memory, and stopping the session expired it. A user could therefore lose an otherwise live browser or text-editing conversation merely by leaving and reopening the phone session.

Saving the reference alone would not repair this. The native owner might have disappeared, and an old mailbox reply could arrive after reconnect. Replaying the original prompt also mixes a read-only recovery question with executable request traffic. A fresh recovery check needs its own correlation ID, must not execute anything, and must leave the original request, accepted answers, form scope, browser account context and deadline intact.

Question persistence is also a state transition. It must replace the pending request only after secure storage succeeds. A newly submitted answer must replace the question before transmission. An older draft-save task or stopped view model must never overwrite that newer answer record.

## Implemented behavior

1. **Advertise recovery only for scoped questions.** The [shared protocol](../../../protocol/Swift/ComputerUseProtocol.swift) adds optional `supportsClarificationRecovery` to explicit question/rejected-answer updates. Missing/false remains the old behavior. The flag is invalid without a scoped intervention question or retry; it does not authorize native continuation.
2. **Use a separate read-only check.** `ComputerUseClarificationProbe` and `ComputerUseClarificationProbeResult` use distinct body discriminators in status envelopes and carry a UUID probe ID plus the exact original reference. Requests are bounded at 2 KiB. An available result contains a complete bounded question and its current optional answer policy; an unavailable result contains no question or policy. These bodies cannot decode as ordinary task updates. They neither change the prompt wire body nor allocate an executable task ID in the ledger.
3. **Check actual ownership after queued sends.** The [host manager](../../../host-mac/RemoteDesktopHost/ComputerUse/HostComputerUseManager.swift) accepts probes only from the authorized controller with ordered-control support. Immediately before replying, it checks transport/authorization generations, the stored reference and prompt identity, and the existing live browser or native text scope. A foreign session/nonce, expired/cancelled question or missing owner returns no actionable question. The [ledger](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseTaskLedger.swift) supplies only the stored matching question text. The probe does not claim a prompt, change controls, interpret a goal, advance an answer or reconstruct an owner.
4. **Save the question before finishing phone recovery.** The [phone pending store](../../../ios/RemoteDesktop/ComputerUse/ComputerUsePendingPromptStore.swift) gains a bounded `ComputerUsePendingQuestion` snapshot: reference, complete text, policy, received time, original deadline and optional exact draft. It remains in the existing device Keychain/account namespace. The snapshot must correspond to its original prompt ID or to the reference in a rejected answer's exact body. It cannot coexist with pending approval or control intent. Pairing-code rebinding retains it. Record age uses the question's original received time, so editing or probing cannot renew retention.
5. **Preserve storage ordering.** The [phone session model](../../../ios/RemoteDesktop/ComputerUse/ComputerUseSessionModel.swift) saves an opted-in question before clearing its active prompt. On failure, it retains the original pending request and does not expose a recoverable answer composer. Successful answer transmission first saves the new exact answer record, then cancels/discards the old question's in-memory save tasks. Normal and rejected-answer questions share this behavior. Legacy unscoped questions and hosts that do not advertise recovery retain their prior behavior.
6. **Require a fresh reply after restart.** A restored question uses `recoveringAnswer`, displays its cached text and disables answer input. Starting the authenticated session sends a fresh probe, rather than replaying the stored prompt. Only the matching probe ID, original reference, selected host/pairing/session and exact question bytes can restore the composer. Old normal replies, old probes and mismatched responses cannot do so. The returned policy is saved before enabling answers. The saved deadline is reused; expired or unavailable questions require an explicit new request.
7. **Bound waiting without inventing confirmation.** A separate ten-second timeout covers a slow or stuck send as well as waiting for a reply. The [view](../../../ios/RemoteDesktop/ComputerUse/ComputerUseView.swift) offers **Check again** after an error/timeout and **Start a new request** while recovery is pending. Each retry uses a new probe ID; stopped/replaced/finished recovery ignores late replies. A currently requested reply can still arrive after the timeout if the user has not superseded that probe. Native answer admission remains authoritative if the owner changes after a probe response.
8. **Retain exact draft bytes.** Draft changes are saved after a short debounce and flushed when a started session stops. Combining-character changes are compared by UTF-8 bytes, not Swift's canonical string equality. Drafts remain bounded by the existing 8,000-character / 32 KiB prompt limits; an oversized draft or failed save reports that it could not be saved, without truncating the live text. Recovery fills an empty composer without replacing another draft.
9. **Keep older instances from replacing newer records.** Before updating, probing, restoring or consuming a waiting question, the model compares its saved record with the currently stored one, including exact prompt, wire-body, question and draft bytes. A replaced record is abandoned without deleting the newer one. Stop is idempotent. These are checks within the current client/store workflow, not a claim of cross-process transactional Keychain behavior.
10. **Retain account handoff boundaries.** Cached questions do not restore browser cookies, prove successful login or approve actions. Existing paused-task records, explicit handback, approval recovery and privacy shielding remain separate. The existing local recovery coordinator still validates account binding and TLS identity before rebinding the record and starting the model; this source change does not bypass that connection path.
