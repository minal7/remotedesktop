# Live ownership before replaying a saved question

Source repair; execution pending. This follows the [rejected browser-answer recovery repair](BROWSER_REJECTED_ANSWER_RECOVERY_REVIEW.md). No build, typecheck, test/assertion run, model invocation, app/browser launch, account login or SSH attempt occurred.

## First-principles findings

A ledger proves what the host previously said. It does not prove that the form, browser session or unresolved task needed to accept the next answer still exists. The host previously replayed a normal clarification reference directly from its terminal record. A browser question could therefore be offered after its native owner was retired, replaced or lost in a host restart. Native text questions had the same gap. Their answer admission would eventually refuse the stale reference, but the phone had already invited the user to answer it.

There was also a timing gap between composing a reply and sending it. Outbound replies wait behind earlier channel operations. A question or rejected-answer retry could be valid when composed and invalid by the time that wait ended. A renewed authorization for the same peer must not release a question queued under an earlier authorization.

The repair separates historical question identity from live continuation authority. It preserves exact-body idempotency and historical terminal records, checks both native and transport state immediately before channel handoff, and reports inability instead of recreating missing ownership. That is a prerequisite for honest reconnect behavior; it is not durable browser or form reconstruction.

## Implemented behavior

1. **Persist the native owner kind with a question.** The [task ledger](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseTaskLedger.swift) records optional private `clarificationOwner` metadata for browser and native text questions. The [manager](../../../host-mac/RemoteDesktopHost/ComputerUse/HostComputerUseManager.swift) derives it from the actual question bridge, independently of whether that owner still passes a liveness check. A failed liveness check cannot turn a known browser question into an unclassified one. No new wire capability or model-authored owner declaration is introduced.
2. **Keep stored kinds scoped and historical.** A classified record requires a claimed, exact-body-bound prompt and a valid intervention question. Invalid/missing question data, inconsistent task identity, unknown kinds and conflicting retry metadata fail ledger loading or completion. Cancel may remove the actionable reference while retaining its historical kind. The first terminal result still wins; replay does not overwrite it with the later recovery failure or run the original prompt again.
3. **Revalidate the browser owner.** The [browser bridge](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserClarificationTransport.swift) requires the same object in the host's owner registry, the same pending question/reference, controller/session, source revision, execution identity and unexpired native question. An old bridge pointer alone is insufficient. Accepted answers and new requests therefore prevent the preceding question from becoming actionable again.
4. **Revalidate the native text owner.** The [text clarification store](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseTextClarificationStore.swift) compares its pending reference with the executor's actual pending question. Task ID, controller/session, original goal, exact question bytes and form scope must agree. The reference must remain unexpired and cannot outlive the native question. Matching visible wording alone cannot authorize a changed form scope, and canonically equivalent but different question bytes do not silently replace the stored question.
5. **Handle unclassified records without guessing.** Older records still decode and retain their historical references. To publish one, the current manager requires a matching live browser or native text question. If neither exists after restart, it returns an inability response without an answer reference. A known browser owner cannot be reinterpreted as a text owner, or vice versa. Older application binaries do not acquire this behavior merely by reading a newer ledger.
6. **Check after the outbound wait.** All scoped questions and browser answer retries capture the current transport and authorization generations. After preceding sends finish, generation/peer mismatches withhold the queued response. Immediately before calling the channel, the manager requires a valid typed update matching the expected task/reference/retry and rechecks native state plus the current ledger reference. Cancel, expiry, accepted answers, retirement and replacement cannot release an actionable stale question from that queue.
7. **Report unavailable recovery without inventing progress.** A missing owner or question produces a typed `unableToComplete` update with no question, answer policy or retry reference. It retains the original reply's control snapshot and any independent historical approved-action evidence; it does not fabricate a newer acknowledgement. The [phone session model](../../../ios/RemoteDesktop/ComputerUse/ComputerUseSessionModel.swift) already handles this terminal outcome by ending pending recovery and returning to a new-request composer. No phone production change was needed for this path.
8. **Retain admission checks after delivery.** The check is at channel handoff. Network/mailbox delay can still outlast a question or its owner. Existing answer admission, nonce matching, native expiry and the phone's deadline remain necessary when an answer eventually arrives. This source repair does not claim the owner must remain live throughout a remote user's editing interval.
