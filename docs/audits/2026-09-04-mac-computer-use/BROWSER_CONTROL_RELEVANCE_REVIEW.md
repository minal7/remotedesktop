# Separate unread values from missing control metadata

Source checkpoint, 2026-09-08. Previous checkpoint: `c9d5835`. Execution remains deferred.

## First-principles defect

The [scoped text reader](BROWSER_READING_SCOPE_REVIEW.md) leaves unselected values unavailable. That is necessary to avoid collecting unrelated account or contact data, but the answer path rejected any page containing an unavailable value. A complete concert result beside an optional newsletter email field therefore could not produce an answer. Reading every field would defeat the scoped reader; ignoring every unread field would conceal potentially relevant search criteria, eligibility or pricing conditions.

There are two different unknowns. Missing control metadata prevents even assessing what the control governs. Visible metadata with an unread value can support a proposed relevance judgment, while leaving the value unknown. That judgment must concern one result under the complete original task. A field unrelated to one offer may still affect another. Neither its absence from selected result fields nor its exclusion as private data establishes irrelevance.

## Source changes

- [Result-page input](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultCandidates.swift) now retains ordered projected control IDs whose native state is unavailable, and a separate native `controlMetadataComplete` fact. Completeness requires the original observation not to report omitted controls, actual control-state observation when controls exist, and every native control's metadata in the projection. The existing `omitted_controls` flag remains true for unread values; no metadata, value state or omission flag is erased.
- [Review input](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResultReview.swift) exposes these unread IDs and bounded metadata/text citation IDs with the complete existing task, requirements, candidates and page context. Review context/schema advances to version 6 when unread controls exist. Other review modes retain their prior contracts.
- [Control relevance admission](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserControlRelevance.swift) requires one ordered row per offered unread control for each candidate. The model proposes `unrelated`, `relevant` or `unknown` and up to eight distinct observed citations. A non-unknown judgment must cite that control's own metadata. Other citations must be observed page text, cannot borrow another candidate's facts, and cannot use another unread control as a substitute. Missing rows, duplicates, reordered/foreign IDs, fabricated evidence, values and extra keys are rejected. A whole legacy response omitting the new member gets an explicit all-unknown mapping; omission cannot clear a dependency.
- An `unrelated` judgment is forbidden without complete control metadata, complete text/structure projection and a goal interpretation. The prompt requires affirmative evidence that the unread value cannot affect the particular result's task criteria, eligibility, price or availability. It explicitly distinguishes a separate newsletter subscription from an account/loyalty field that may govern an offer. Missing values, private-data exclusions and the desire to complete the task are not evidence of irrelevance.
- [Answer eligibility](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserResearchAnswer.swift) now checks missing-value dependencies per candidate. All unread controls must have an admitted `unrelated` judgment for that candidate. Any relevant/unknown row, missing metadata or incomplete projection still excludes it. A zero-length list cannot waive genuinely omitted controls. All existing result requirements, pure result-text support, quantity checks, source policy, full passages, control observations and delivery bounds still apply. Unread metadata cannot supply a result fact or an observed value. The answer continues to display the retained unavailable control state separately from page prose.
- Relevance rows enter the exact review digest and current/historical planner context. Existing source/goal ownership, native page revalidation and Pause/handback invalidation apply to them. A changed label or surrounding qualification invalidates the earlier reading; explicit handback requires a fresh reading/review. This adds no permission to collect values, edit a form, log in or perform an effect.
- [Segmented review](../../../host-mac/RemoteDesktopHost/ComputerUse/ComputerUseBrowserReviewParts.swift) partitions control rows over the same immutable input. Every request still carries the complete context; each response contains only the requested IDs. Control output is included in conservative size bounds, with at most four control rows per part. Whole output and each part remain bounded by the existing 896-byte canonical estimate, at most 32 parts and the existing shared review deadline. Final assembly requires exact control coverage/order and matching candidate associations before re-running full native admission. Its schema is `browser_result_review_part_v5`. Control review can increase the number of bounded parts; it is not a new independent planner or an unbounded loop.

This removes an unconditional rejection, conditional on a semantic review. It does **not** establish that the model correctly understands arbitrary account fields, custom widgets, languages or provider relationships. Citations prove which metadata the proposal used, not that its interpretation is true. A mistaken `unrelated` judgment remains a model qualification risk. The source boundary must be exercised with both clearly unrelated fields and adversarially similar fields that actually govern price, membership, location or availability before readiness can be claimed.
