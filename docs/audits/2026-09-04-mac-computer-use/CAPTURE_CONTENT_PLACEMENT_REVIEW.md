# Use one full-display rectangle for capture, video and input

This extends [display binding](CAPTURE_DISPLAY_BINDING_REVIEW.md) and the [configuration notification fence](CAPTURE_DISPLAY_CHANGE_REVIEW.md). Apple and upstream source documentation was retrieved read-only.

## Confirmed mismatch and construction

The host previously checked a frame's outer pixel dimensions but discarded its content rectangle, display density and content scale. Capture preserved source aspect ratio inside an even-sized output. The phone independently aspect-fitted the logical display size for input while asking its renderer to aspect-fit the decoded pixel size for video. Those calculations need not produce the same rectangle. The Metal drawable size is also rounded independently, adding another possible aspect-ratio difference.

Apple's [WWDC22 capture guide](https://developer.apple.com/videos/play/wwdc2022/10155/) explicitly describes letterboxing for full-display capture when source and output aspect ratios differ. It also explains why per-frame content placement and scale matter. Outer buffer width/height alone cannot establish the mapping.

The repair constructs a full-surface mapping: capture fills the encoded surface; the phone fits the logical display rectangle into its viewport, then fills that same rectangle with the decoded surface. The two axis scales can differ slightly at capture because codec dimensions must be even. Applying the inverse logical aspect ratio at display avoids introducing an independent video letterbox inside the input rectangle. This is source-level construction and validation, not evidence of the pixels a native renderer actually presented.

## Native frame admission

[CaptureVideoPlacement](../../../host-mac/RemoteDesktopHost/ScreenCapture.swift) reads each sample's `contentRect`, `scaleFactor` and `contentScale`. Rectangle dictionaries and numeric scalars must have the expected types and finite values; booleans, strings, missing fields, nonpositive content dimensions/scales and invalid display density are rejected. It retains an optional Presenter Overlay rectangle on supported systems. The resulting placement is immutable and belongs to the same sample as its image and capture-clock metadata.

The installed [ScreenCaptureKit header](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ScreenCaptureKit.framework/Headers/SCStream.h:423>) describes content rectangles in surface points, display density as the pixel-to-point factor, and content scale as the scaling already applied to the source. The surface rectangle is therefore multiplied by display density to obtain pixels. Multiplying content scale into that placed rectangle again would scale it twice. Apple's [capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) retrieves these fields separately as well; its Markdown documentation was read after the web reader could not display that content type.

The [stream configuration](../../../host-mac/RemoteDesktopHost/ScreenCapture.swift) now disables aspect-ratio preservation and explicitly sets the destination rectangle to the complete output surface. The source rectangle remains unset, which the [SDK contract](</Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/ScreenCaptureKit.framework/Headers/SCStream.h:286>) defines as capturing the entire selected display. The captured display/filter/configuration remains bound to the exact native attempt and configuration token.

Before source availability or encoding, each frame must have the configured outer dimensions, matching display density and content occupying the full pixel surface. A 0.001-pixel tolerance covers serialization rounding, not a pixel of padding. Density comparison permits a 0.000001 difference. These are explicit numeric tolerances awaiting native qualification. Nonempty Presenter Overlay placement is currently unsupported for direct-control capture; it cannot silently become an ordinary desktop mapping.

Missing, malformed, padded, cropped, density-mismatched or overlaid output enters the existing unavailable path. That path revokes input and waits for qualifying complete output within the existing recovery budget. This repair does not infer a crop from an unknown frame, bypass its metadata or grant a fresh budget on each invalid frame. A later valid sample retains the existing capture-time recovery requirement.

## Wire and phone behavior

The descriptor-based [layout encoder](../../../host-mac/RemoteDesktopHost/WireFormat.swift) adds `fullDisplaySurface: 1` after the capture path has established availability. [DisplayInfo and decoding](../../../ios/RemoteDesktop/Protocol/WireFormat.swift) retain that marker with the input acknowledgement. An absent marker preserves earlier presentation; an unknown/malformed marker closes the session. Display dimensions now require positive exact signed-32-bit JSON numbers and density in `[1, 4]`. Legacy omission of density still defaults to one. Previous string/fraction coercion and unchecked large-number conversion are removed for display geometry.

[RemoteScreenRenderingLayout](../../../ios/RemoteDesktop/Session/RemoteScreenView.swift) uses the same logical aspect-fit rectangle as input for full-surface displays. It places the video view inside that rectangle and uses scale-to-fill within it. Legacy displays retain the earlier whole-viewport aspect-fit renderer. Layout publication updates the video rectangle immediately and also schedules UIKit layout; pointer coordinates and video placement both use the content view's local bounds. Existing viewport zoom transforms the shared content view, so its video, cursor and inverse point conversion continue to share that transform.

The public installed RTCMTLVideoView header exposes its video content mode. The [reviewed M144 reference implementation](https://github.com/webrtc-sdk/webrtc/blob/30d5e63ae91da483e06577b5c35ee91cc5e5c3db/sdk/objc/components/renderer/metal/RTCMTLVideoView.m) forwards that mode to its Metal view, lays the Metal view out in its bounds, and schedules size updates on the main queue. This is an upstream reference, not established source provenance for the installed LiveKit binary. The separate [media proof limitations](CAPTURE_FRAME_EVIDENCE_REVIEW.md#detailed-sequence-to-close-the-actual-recovery-gap) remain.

The [wire contract](../../../protocol/PROTOCOL.md#display-host--client) documents these semantics. The marker asserts spatial placement; it does not identify which captured frame reached the owning renderer. A data-channel layout and an unrelated frame probe still cannot prove current presented pixels. Earlier hosts do not gain full-surface validation, and earlier phones may ignore the marker; mixed-version behavior is unqualified.
