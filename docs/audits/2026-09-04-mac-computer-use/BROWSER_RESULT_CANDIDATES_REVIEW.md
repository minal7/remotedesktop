# Bind candidate readings to exact browser sources

Date: 2026-09-07. Parent source: 5c0ea41. New candidate-reading planner, runtime entry point and native preparation/revalidation methods. **No general research driver, verified offer output or public source-link publication is enabled.**

## First-principles finding

An offer is more than a collection of words from a page. Equal prices in neighboring cards do not establish the same ticket, a global date header may apply to multiple results, and a price paragraph may be qualified by “excluding fees” elsewhere in its card. A shared ancestor can contain multiple offers. A result link may wrap an entire card rather than sit inside it. Result preparation must retain these relationships and unknowns, while later verification must establish their meaning.

The existing DOM tree and planner context provide structural evidence, but the normal action projection prioritizes controls and does not supply result records that can be checked against their source later. This change adds a reading-specific projection, bounded model reference selection and source-bound candidate records. It deliberately does not turn model grouping into a verified offer, arithmetic observation or completion decision.

## Implemented behavior

1. ComputerUseBrowserResultPageInput validates and retains the exact host snapshot, then builds a bounded text/link/container projection through the existing context builder. Controls, current values, submission metadata and destination URLs are not included in the reading projection. Controls are explicitly marked omitted when present. Existing source, structure, embedded-content and projection omission markers survive. Only actually projected text/link/container IDs are eligible for model selection.
2. ComputerUseBrowserResultProposal accepts a strict, duplicate-key-checked schema containing up to eight candidate groups. Each names a known non-root content container, one to sixteen fields with complete source text IDs, exactly one title field and up to sixteen selected link IDs. Total references are capped at 128. No free-form fact value, URL, action, answer, ranking or completion field exists.
3. Field references must be exposed, unique, in source order within their field and inside the selected subtree. Overlapping or ancestor/descendant candidate groups, missing titles, duplicate references, unknown IDs, cross-subtree facts and references that only exist outside the projection are rejected. Candidate groups are returned in document order, which is not asserted to be a price or preference ranking.
4. Selected links must be structurally inside the candidate or wrap its actual text. In the latter case the observed link container can be an ancestor, but it must have nonempty text references and every reference must belong to this one candidate. Shared/global links and links that refer to another candidate cannot become that candidate's selected source. The model cannot supply a destination.
5. A selection still interprets the container and field roles. A prepared case deliberately accepts a broad container containing neighboring offers: a common ancestor does not prove association. Likewise, disjoint cards can repeat the same real-world offer. Container uniqueness does not prove the requested count of distinct tickets/results.
6. ComputerUseBrowserResultCandidates retains every text and link structurally associated with each selected subtree, not just the model-selected fields. Unclassified and unprojected text/link IDs remain explicit. Surrounding page text/links and the full container tree remain separate. Thus fee notes, sold-out notices, global filters/dates and other unassigned context are not silently dropped. Exact destination URLs stay within the retained private page evidence; candidate link records expose only observation IDs, labels and text references.
7. Candidate IDs bind the goal revision, native document context/generation/identity, snapshot, container, field references and selected link references. They identify this observation/interpretation, not a stable real-world offer across pages. The batch retains all source/projection omission flags and contains no “all passed,” normalized scalar observations or completed answer.
8. ComputerUseOwnedBrowser.prepareResultCandidates requires the proposal's goal revision and original root to match the supplied goal/document, and requires the proposal's complete snapshot to match the retained native evidence. It then revalidates that evidence through the existing WebKit boundary before returning records. Cancellation, authentication, presentation and ownership checks remain in force around the await. No link or input is dispatched.
9. validateResultCandidates checks the batch against the supplied current goal and revalidates its live native source again. Replaced DOM objects, changed pages, lost control and authentication barriers cannot be hidden by identical text or a previously prepared batch. Records become historical after navigation; this API does not certify them as current across pages or establish website truth. The eventual driver must supply its actual current goal revision rather than a retained stale copy.
10. ComputerUseLocalBrowserResultPlanner receives the complete structured original goal and clarification answers alongside separate untrusted page JSON. It outputs only observed-reference proposals. The original clock remains fixed, while question/context text is not user instruction authority. Private task, controller, question, revision and document identifiers are omitted from model context.
11. The complete request is counted once against the existing 4,096-token context, 1,024-token output allowance and 64-token reserve, with no goal/page reduction retry. Nonpositive/oversized counts stop before inference. Cancellation is checked before counting, before inference and before publishing a proposal. A shared browser-only response helper preserves the existing expected-alias, one stopped assistant choice, duplicate-key, tool-call/refusal and size/UTF-8 admission rules. Native form/tool decoders are unchanged.
12. ComputerUseRuntimeBrowserResultPlanner and OSAtlasLlamaRuntime.proposeBrowserResults use the existing verified native installation and model owner. They retain the model-access lease through resource admission, counting, inference, decoding and endpoint/cancellation checks. This is a callable component, with no new server process, lifecycle optimization or host research-route caller.

An empty candidate list is only an empty interpretation of this projection. It does not prove that the site has no matching results. Default candidate, text, link, batch, input and proposal descriptions omit source contents and destinations. This does not sanitize arbitrary page text/labels or qualify shareable URLs.

## Prepared verification and actual checks

Seven new planner/proposal methods cover reading projection and private-field omission, separate equal-price cards, source-order and reference validation, unknown/duplicate/invented data, overlapping groups, wrapped-card versus shared links, deliberately unresolved broad-ancestor meaning, projection limits, missing/malformed structure, complete clarified-goal input, exact token admission, response integrity and cancellation.

Three new native DOM methods cover full text/link retention and separate global context; goal/snapshot mismatch; native wrapper replacement with identical source text; fresh rebinding; and authentication, control loss and cancellation during preparation. They also assert that result links are not navigated. These are prepared WebKit fixtures, not executed browser tests.

The two new implementation files and new test class are registered in Xcode; SwiftPM and project.yml already include their directories. The [focused source inventory](browser-result-candidates-inventory.json) selects **251** methods and the default selects **773**. Six changed/new Swift files pass syntax-only parsing. The two new fixture scripts pass JavaScript syntax checking. Project-file syntax, exact source inventories and whitespace checks pass. **No typechecking, assertions, model calls, builds, app launches, WebKit fixture execution or computer-use activity ran.** The new prompt/schema/runtime path, provider behavior and full research workflow remain unqualified. The installed app is unchanged.
