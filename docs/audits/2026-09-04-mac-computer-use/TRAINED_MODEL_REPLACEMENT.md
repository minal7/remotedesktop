# Replacing OS-Atlas with a trained computer-use model

The user requires OS-Atlas replacement, test-driven development, and a **12 GB total Mac RAM** target. The current status and execution evidence remain in [TODO.md](../../../TODO.md). This document records the model decision, not another tracker.

The present Qwen3.5-4B general model successfully interpreted six form-editing cases and drove a visible two-field task through login pause and shipped-client TLS Resume. It failed a simple concert-research request before navigation: source clauses were omitted and question references did not exist. Disabling thinking did not repair the response. These failures remain recorded and the production decoder still rejects them. More custom source-clause prompt rules are not the next step.

Fara uses 0–1000 normalized coordinates and a single `computer_use` tool call, with distinct question and terminal actions. Its page-reading helper uses the same model.

## Reuse the controls, replace the actor

Keep the app-owned capture identity, checked input delivery, task ledger, cancellation, login detection and explicit Resume. Replace OS-Atlas's model-specific observation/prompt/action adapter. The current visual path hard-codes Phi3/InternVL formatting, 256 image tokens and 256 output tokens; the native text path disables the projector. Swapping manifest URLs would therefore be insufficient. The [pinned llama.cpp converter](https://github.com/ggml-org/llama.cpp/blob/6eddde06a4f25d55d538b5d15628dcc2b6882147/conversion/qwen3vl.py) supports the relevant Qwen3.5/Qwen3-VL architectures, but exact-conversion loading must be demonstrated.

The model supplies a proposed next action. A parsed click is not authority to act on a stale screen, and a terminal answer is not independent proof that the task succeeded. The existing host controls retain those responsibilities. Parsing must preserve exact text, accept only supported typed arguments, reject duplicate/multiple/truncated calls, and bind coordinate conversion to the current captured image.

## Resource evidence and next experiment

A 12 GB Mac currently selects the compact profile, including a 4 GiB model-process ceiling. Fara's staged weights alone are 3.31 GiB, so the existing ceiling may be too small for cache and image workspace. Do not raise it merely from weight size. A planning estimate is 4.5–6.5 GiB for Fara/Holo inference with bounded context plus 1–2 GiB for host/WebKit/capture; macOS and other applications are additional. This is an estimate, not acceptance. A [community MLX 8-bit probe](https://huggingface.co/mlx-community/Fara1.5-4B-8bit) reports 6.15 GB peak on a 32 GB M2 Pro, but explicitly lacks agentic evaluation and does not qualify this app or Q4 runtime.

Run adapter regressions before effects. Then use one frozen local browser image, Fara's native prompt, the pinned Q4/projector pair and one bounded inference process. Require a correctly decoded target/text proposal and record elapsed time and peak footprint. Next run the two-edit/login/Resume fixture, followed by the original concert request, then one travel and one movie case, sequentially and stopping on the first failure. Test Holo on the same inputs if Fara fails a meaningful native-format trial. Defer RTX3080 distillation until a working execution path and fixed evaluation set identify a need.

## First native Mac trial

The pinned Q4/projector pair loaded successfully with the app's signed llama.cpp b9992 binary. One frozen native WebKit form was supplied as an image, followed by “Click the Destination field.” The model was not given DOM labels, element bounds, the expected coordinate or an action grammar. It produced `left_click` at normalized `[392, 540]`. The compiled Swift decoder mapped that to the actual 2376×1536 image; an XCTest independently checked that the point falls inside the field's DOM bounds with an eight-point inset. No input was executed.

The first response exposed a harness mismatch: llama.cpp's automatic reasoning parser put Fara's complete native response in `reasoning_content` and left `content` empty. The original check failed. Fara's [official parser](https://github.com/microsoft/fara/blob/a675d6d61c41c47ae87bacefeab22caad18e3e84/src/fara/agents/fara/fara15_agent.py#L404) expects narrative followed by a tool call. The next probe used the [documented `reasoning_format=none` response option](https://github.com/ggml-org/llama.cpp/blob/6eddde06a4f25d55d538b5d15628dcc2b6882147/tools/server/README.md#post-v1chatcompletions-openai-compatible-chat-completions-api), preserving raw output without disabling thinking or changing the model prompt. A separate native-message adapter discards narrative and validates the entire remaining call. It does not recover executable actions from a separate reasoning field. Duplicate/multiple/malformed calls and trailing prose remain rejected; literal tool tags inside typed strings remain unchanged.

The successful proposal used 8,192 context tokens, a 1,536 image-token ceiling, 1,024 maximum generated tokens, four CPU threads, one slot, GPU offload, no prompt cache and zero busy polling. Startup took 2.60 seconds and generation 8.35 seconds; the response used 3,223 prompt and 45 completion tokens. Peak **sampled process RSS** was 4,167,909,376 bytes (3.88 GiB). This excludes unsampled peaks, other app processes and complete Metal/physical-footprint accounting. It is not 12 GB or thermal qualification, nor proof that the production 4 GiB resource ceiling is sufficient. The exact owned process exited and its temporary credential was removed.

Seven new methods have successful results: four strict action/coordinate cases, native narrative separation, the local WebKit fixture and actual proposal/oracle validation. Red results are retained for the initial throwing action decoder and native-format adapter. The first fixture rendered successfully but crashed during AppKit window cleanup; setting the task-owned window's `isReleasedWhenClosed` to false repaired that test-only ownership defect, and the fixture then passed. Evidence is retained in `.build/repair-verification/fara-replacement-verification.json`, its named xcresults, and `TrainedComputerUseModels/Fara15/{fixture-02,proposal-03}` under verification DerivedData.

The next integration should reuse the existing owned browser, input checks, cancellation and login handback, with a Fara-specific observation/request/action adapter. Do not route Fara through the general model's source-clause planner or OS-Atlas's Phi3 visual prompt. Prove the complete two-field/login/Resume task before attempting the previously failing concert request. The downloaded assets and standalone action decoder are not yet wired into the app's executor or installer.
