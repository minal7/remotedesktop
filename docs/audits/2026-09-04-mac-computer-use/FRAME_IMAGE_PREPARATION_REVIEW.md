## First-principles requirement

A renderer replacement must account for both hardware-decoded pixel buffers and software-decoded planes. Accepting only CVPixelBuffer would leave ordinary software frames unsupported. Converting every unknown buffer through `toI420()` is also insufficient: conversion can allocate, discard format information and hide an unsupported source behind an apparently successful image. Plane dimensions, strides, active bytes, color interpretation and ownership must be explicit before encoding a drawable.

The installed LiveKit headers expose `RTCCVPixelBuffer` crop/adaptation metadata and the native `LKRTCI420Buffer` class with width, height, chroma size, strides and plane pointers. The inspected M144 [Objective-C bridge reference](https://raw.githubusercontent.com/webrtc-sdk/webrtc/30d5e63ae91da483e06577b5c35ee91cc5e5c3db/sdk/objc/native/src/objc_frame_buffer.mm) wraps non-native output in its I420 class. The [native I420 implementation](https://raw.githubusercontent.com/webrtc-sdk/webrtc/30d5e63ae91da483e06577b5c35ee91cc5e5c3db/sdk/objc/api/video_frame_buffer/RTCNativeI420Buffer.mm) exposes those retained planes directly. These references support the source path; they do not prove the installed binary's behavior or native decoding coverage.

## Implemented preparation

[RemoteVideoFrameImage](../../../ios/RemoteDesktop/Transport/RemoteVideoFrameImage.swift) returns a typed prepared image, unsupported input, or resource failure. The existing NV12 full/video-range and BGRA/ARGB CVPixelBuffer path retains its original buffer and attachments, then applies the actual wrapper crop, adaptation and rotation. It does not copy or round the wrapper's metadata a second time. Unsupported CV formats do not fall through to a lossy conversion.

The software path accepts the native I420 wrapper class directly, checks that its dimensions agree with the frame, requires positive bounded geometry, and validates ceil-divided chroma dimensions and every stride/span before reading. Dimensions are bounded by the existing 3840-pixel policy; each addressable plane span is capped at 64 MiB with overflow-checked arithmetic. These are preflight limits, not measured memory budgets. Raw plane storage still relies on the retained native buffer honoring its public geometry/stride contract; metadata cannot independently prove a pointer's allocated length.

The source is copied into a newly allocated, CPU-writable, Metal-compatible NV12 buffer. Output allocation, plane geometry, base-address locking, pointers, row spans, copy completion and unlocking are checked. A pure packing helper validates all source/destination capacities before any writes. It copies visible luma and U/V samples only, interleaves U then V, and initializes destination row padding. It never reads source row padding, including trailing bytes after the last active row. Source and destination storage must be disjoint, as they are in the production allocation path.

Odd dimensions use even backing storage. The final visible luma column and row are extended into the one-pixel backing edge; chroma uses ceil-divided dimensions. The image is cropped back to the visible top-left rectangle before adaptation and rotation. This preserves the last chroma sample rather than floor-dividing it away. Native chroma reconstruction and filtering at odd boundaries still need pixel qualification.

The [producer](../../../ios/RemoteDesktop/Transport/RemoteVideoPresentationProducer.swift) reserves its shared presentation capacity before preparation. Unsupported input abandons that uncommitted ticket and returns `.unsupportedFrame`; allocation/locking/preparation failure abandons it and returns `.preparationFailed`, separately from command encoding failure. Prepared pixels and the lazy Core Image graph are retained by the command's completion resources until actual GPU completion. Retirement/expiry still cannot free committed unfinished GPU work. No new producer, timer, display loop or inference worker was activated.

## Explicit color boundary

The public Objective-C frame/I420 interfaces inspected here do not carry a source color profile. The existing M144 [I420 shader reference](https://raw.githubusercontent.com/webrtc-sdk/webrtc/30d5e63ae91da483e06577b5c35ee91cc5e5c3db/sdk/objc/components/renderer/metal/RTCMTLI420Renderer.mm) uses normalized luma without a video-range expansion and fixed YUV-to-RGB coefficients. That is evidence for a compatibility default, not proof of the source's actual matrix, range, primaries or transfer function.

The staging path therefore explicitly marks **full-range BT.601 YCbCr, centered chroma, Rec.709 primaries and sRGB transfer**. Core Video defines the [full-range NV12 format](https://developer.apple.com/documentation/corevideo/kcvpixelformattype_420ypcbcr8biplanarfullrange) and [BT.601 matrix attachment](https://developer.apple.com/documentation/corevideo/kcvimagebufferycbcrmatrix_itu_r_601_4); their declarations and the transfer/chroma keys were inspected in the installed SDK. This is a declared SDR interpretation. It is not reconstructed source metadata, a colorimetrically qualified conversion, or a guarantee of exact parity with the old shader. Core Image can differ in chroma interpolation, clipping and color management.

Before activation, qualify decoded grayscale/color ramps and edges for the actual negotiated formats. Where source range/profile differs or must be preserved, carry authoritative color metadata through the codec bridge or define and enforce a matching negotiated SDR contract. Do not silently label unknown HDR, wide-color or video-range I420 as qualified by this default. Unknown buffer implementations, including arbitrary objects that merely offer a conversion method, remain unsupported.
