# Keyboard ownership during manual handoff

Source repair, 2026-09-10, following `4571b8b`. Native UI, tests, model runs and website execution remain deferred. This records a client input repair; complete Mac browser/login handoff is still unqualified.

## First-principles findings

A connected keyboard is an input device, not proof that its events belong to the remote desktop. The prior hardware path sent keys from the global GameController handler while its SwiftUI capture was mounted. That callback did not establish the UIKit first responder, originating window or local control receiving a press. A delayed view update is also insufficient to stop input immediately when the user returns control to the AI.

The Computer Use chat field is already disabled during the current manual-control interval. This review did **not** confirm that typing in that disabled field was simultaneously sent to the Mac. The confirmed source gap was the lower-level global forwarding path and its dependence on view retirement. Local dialogs, focus changes, window changes and fast task-state transitions need their own ownership boundaries.

Apple describes hardware keyboard input through the [responder chain](https://developer.apple.com/documentation/uikit/handling-key-presses-made-on-a-physical-keyboard). A [UIPress](https://developer.apple.com/documentation/uikit/uipress) exposes its responder, originating window, key and current phase. GameController's local SDK `GCKeyboardInput.h` recommends UIKit/AppKit for text input and describes its device-level polling/event role. These contracts support responder-based routing; they do not qualify this implementation's actual keyboard-service chronology.

A release must belong to the same owned press as its down. A HID usage alone cannot identify that lifetime. Modifier flags describe a sampled state; they do not identify the physical left/right key or prove this capture owned its down. Treating an unobserved modifier as a guessed left-side hold, or dropping it and typing the plain character, can change the user's intended operation.

## Source changes

[RemoteHardwareKeyboardCapture](../../../ios/RemoteDesktop/Session/RemoteHardwareKeyboardCapture.swift) is now a native responder. The [SwiftUI wrapper](../../../ios/RemoteDesktop/Session/KeyboardCapture.swift) installs, updates and retires it. Hardware forwarding consumes only keyboard presses whose native responder and originating window match that capture, while it remains the first responder in a key window with current session/source authority and no presented root controller. Unsupported or foreign presses continue to the superclass.

One capture may acquire one responder lifetime. Resignation, window loss, device disconnection, scope loss or teardown retires its source and releases owned keys. It cannot claim a successor source after retirement. Both parent views identify hardware and soft captures with the input generation plus a separate keyboard-focus generation. An old hardware view checks that complete identity even before SwiftUI dismantles it.

Initial capture requires no other first-responder view in the window. The view-tree check reads responder ownership only, without reading text. An admitted new button press inside the remote content rectangle can request a new, one-use capture identity and explicitly reclaim focus. Hover, scrolling, margins and local chrome do not request focus through this path. Clicking while the current remote responder already owns a valid source does not release an existing modifier, preserving combinations such as Command-click. An already-presented controller still prevents focus acquisition.

GameController no longer forwards keys. Its device notifications track attachment, and a temporary handler observes only an all-keys-released boundary when capture begins with keys already held. This prevents that known initial hold from becoming a new remote press. The handler is cleared at that boundary or retirement. Native callback ordering across GameController and UIKit is still a qualification requirement.

Press state records exact native object identity and HID usage. The capture retains admitted native objects until release/retirement, preventing address reuse while a press remains owned. Foreign, duplicate and mismatched releases cannot release a replacement. Force-change callbacks do not create repeats; repeated native began callbacks may preserve key-down repetition. Modifier events are processed before ordinary key-downs in a batch and after ordinary releases. Left/right bits come from owned physical downs; sampled flags cannot manufacture a missing modifier source. New ordinary presses carrying an unowned modifier are consumed without remote input. Caps Lock uses the native alpha-shift state. System-reserved shortcuts remain subject to [UIKit's keyboard-command handling](https://developer.apple.com/documentation/uikit/uikeycommand).

[SessionModel](../../../ios/RemoteDesktop/SessionModel.swift) permits keyboard captures in Computer Use only while the prompt channel is connected, the screen is available/uncovered and the task is paused. Returning to AI control or stopping the prompt channel synchronously ends hardware, soft-keyboard and latched-modifier sources and rotates the keyboard-focus identity. This happens before a subsequent paused state could revive an old capture. Pointer ownership and the visual/TLS connection retain their existing independent policies. General direct-input transport admission is not redefined as a keyboard-only policy; this patch scopes the native capture paths.

Source cleanup can call back into task control. [Take Control, Resume and Stop](../../../ios/RemoteDesktop/ComputerUse/ComputerUseSessionModel.swift) now recheck their task/operation generation after publishing the state transition, before scheduling or persisting the outgoing control. A reentrant Take Control during keyboard cleanup therefore supersedes the interrupted Resume.
